第 0 节

从你家到 YouTube 的服务器

嗨，我是 Carrie Anne，欢迎收看计算机科学速成课！上集讲到，你的计算机连在一个巨大的分布式网络上，这个网络叫互联网。我知道这一点，因为你正在看一个 YouTube 视频，它正是通过互联网传过来的。互联网是一张不断扩大的、由互相连接的设备组成的网。

你的计算机要拿到这个视频，第一个连接是你的局域网（LAN），可能就是你家里所有连着 WiFi 路由器的设备。局域网再连到广域网（Wide Area Network，WAN），通常是你的互联网服务提供商（Internet Service Provider，ISP）运营的路由器，比如 Comcast、AT&T 或 Verizon 这样的公司。一开始是一个区域路由器，比如覆盖你所在街区的；然后这个路由器连到一个更大的 WAN，可能覆盖整个城市或城镇。中间可能还要再跳几次，但最终你会连到互联网主干（backbone）——由一群巨型路由器组成，它们之间有带宽超高的连接。

为了向 YouTube 请求这个视频文件，一个数据包要先一路往上到达主干，在主干上走一段，然后再一路往下，到达一台存着这个文件的 YouTube 服务器。可能是往上 4 跳、沿主干 2 跳、往下 4 跳，一共 10 跳。如果你用的是 Windows、Mac OS 或 Linux，可以用电脑上的 traceroute 程序，看看数据去往互联网上不同地方所走的路线。

对我们这些在印第安纳波利斯 Chad & Stacey Emigholz 工作室的人来说，到加州 DFTBA 服务器的路线要经过 11 站。从 192.168.0.1 出发——这是我的电脑在我们局域网里的 IP 地址；然后是工作室的 WiFi 路由器，接着是一串区域路由器，然后进入主干，再一路往下，到达托管 DFTBA.com 的计算机，它的 IP 地址是 104.24.109.186。

192.168 开头的地址是怎么回事 192.168.x.x、10.x.x.x 这类是"私有地址"，只在局域网内部有效，全世界无数个家庭都在用同样的 192.168.0.1。出门上网时，家里的路由器会把它换成 ISP 分配给你的公网地址（这叫 NAT）。你本机开发时常用的 localhost 则是 127.0.0.1，代表"这台电脑自己"。

但数据包到底是怎么过去的？如果它在路上丢了怎么办？我在浏览器里输入 "DFTBA.com"，浏览器怎么知道服务器的地址？这些就是今天的话题！

第 1 节

IP 与 UDP：送到哪台电脑、哪个程序

上集说过，互联网是一个巨大的分布式网络，它把数据切成一个个小数据包来传送。如果你的数据够大，比如一个邮件附件，就可能被切成很多个包。比如，你现在看的视频流，就是以一连串数据包的形式到达你的电脑的，而不是一个巨大的文件。

互联网上的数据包必须遵守一个标准，叫互联网协议（Internet Protocol，IP）。这很像通过邮政系统寄实体信件：每封信都要写一个唯一的、清楚的地址，包裹的尺寸和重量也有限制。违反了这些规定，信就寄不到。IP 数据包也很类似。但是，IP 是一个非常底层的协议——数据包的头部里除了目的地址之外，几乎没有别的东西。头部就是存放在数据载荷（payload）前面的元数据（metadata，"关于数据的数据"）。这意味着一个数据包到了某台计算机，这台计算机可能不知道该把数据交给哪个程序：Skype，还是《使命召唤》？

因此人们开发了一些更高级的协议，位于 IP 之上。其中最简单也最常见的之一，是用户数据报协议（User Datagram Protocol，UDP）。UDP 有它自己的头部，这个头部位于（IP 包的）数据载荷里面。UDP 头部里有一些有用的额外信息，其中之一是端口号（port number）。每个想访问互联网的程序，都会向所在计算机的操作系统申请一个唯一的端口，比如 Skype 可能申请 3478 号端口。数据包到达计算机时，操作系统会查看 UDP 头部，读出端口号，比如看到 3478，就把数据包交给 Skype。

动手：数据包到了，交给谁？

总结一下：IP 负责把数据包送到正确的计算机，UDP 负责把数据包送到这台计算机上正确的程序。

你天天在用的端口 网址 http:// 默认用 80 号端口，https:// 默认用 443。跑 npm run dev 时终端提示的 localhost:5173，就是 Vite 开发服务器向操作系统申请了 5173 号端口；如果提示"端口被占用"，意思就是已经有别的程序拿着这个号了。
第 2 节

校验和

UDP 头部里还有一个东西叫校验和（checksum），用来验证数据是否正确。顾名思义，它是靠检查数据的"和"来做到的。下面是简化版的原理。假设我们的 UDP 包里，原始数据是 89、111、33、32、58 和 41。发送之前，发送方计算机把所有数据加在一起来算校验和：89 加 111 加 33，以此类推。在这个例子里，加起来得到校验和 364。

UDP 中，校验和用 16 位来存。如果和超过了能表示的最大值，最高的几位就会溢出，只用低位。接收方计算机收到这个包后，重复同样的过程，把所有数据加起来。如果这个和与头部里发来的校验和一样，就一切正常；如果对不上，你就知道数据在传输途中某个地方损坏了，也许是因为电压波动或者电缆有毛病。

简单求和的盲点 试试"交换两个数的位置"：数据顺序乱了，但和没变，校验和就发现不了。所以真实的校验和（以及 TCP 用的、各种文件下载用的哈希）会用更讲究的算法，让这类错误也能被查出来。课程里讲的是最简化的版本。

不幸的是，UDP 不提供任何修复数据或者请求重新发一份的机制：接收程序会被告知数据损坏了，但通常只是把这个包扔掉。而且，UDP 没有任何机制能知道数据包有没有送到：发送方把 UDP 包发出去，但永远得不到它成功抵达的确认。

这两个特性听起来都很要命，但有些应用不在乎，因为 UDP 也非常简单、非常快。比如 Skype 用 UDP 来做视频聊天，它能应付损坏或缺失的包。这就是为什么网络不好时，Skype 会变得卡卡的——只有一部分 UDP 包到了你的电脑。

第 3 节

TCP：一个都不能少

但很多其他类型的数据传输不能这样。比如你发一封邮件，它到达时中间缺了一段，这可不行。整封邮件必须完整无误地送到！当数据"绝对、必须送到"时，程序会用传输控制协议（Transmission Control Protocol，TCP）。和 UDP 一样，它也装在 IP 包的数据载荷里。因此，人们把这个协议组合称作 TCP/IP。

和 UDP 一样，TCP 头部里也有目的端口和校验和。但它还有一些更高级的功能，我们重点讲几个关键的。

第一，TCP 数据包有连续的序号。15 号包后面是 16 号包，再后面是 17 号……一次会话里可能发出几百万个包。这些序号让接收方计算机能把包排成正确的顺序，即使它们经过网络、在不同的时间到达。所以就算一封邮件到达时顺序全乱了，你电脑操作系统里的 TCP 实现也会把它正确地拼起来。

第二，TCP 要求一台计算机正确收到一个包——并且数据通过了校验和检查——之后，给发送方回一个确认（acknowledgement），酷小孩们管它叫 "ACK"。知道这个包成功送到了，发送方就可以发下一个包。但假设这一次，发送方等着等着，没收到确认包。一定是哪里出了问题。如果等了足够长的时间，发送方就会直接重发同一个包。

值得一提的是，原来那个包可能其实已经到了，只是确认被延误得很厉害；或者丢的是确认包本身。不管哪种情况都没关系，因为接收方有序号，如果来了一个重复的包，扔掉就行。

动手：同一段旅程，TCP 和 UDP 各会怎样

另外，TCP 不限于一来一回地对话——它可以连发很多个包，同时有很多个 ACK 还没回来。这大大提高了带宽，因为不用把时间浪费在等确认包回来上。有趣的是，ACK 的成功率，以及从发送到收到确认的往返时间，可以用来推断网络拥塞的程度。TCP 用这些信息来调整发包的激进程度——这是一种拥塞控制机制。

所以，TCP 基本上能处理数据包乱序到达、丢包（包括重发），甚至能根据可用带宽调节自己的发送速率。相当厉害！

你可能会问，既然 TCP 有这么多好功能，为什么还有人用 UDP？最大的缺点就是那些确认包——它们让网络上的消息数量翻了一倍，却没有多传任何数据。这些开销，以及随之而来的延迟，有时候不值得换来的那点可靠性，特别是对时间要求很高的应用，比如多人第一人称射击游戏。如果你就是那个因为卡顿被打爆的人，你肯定同意！

浏览器里的 TCP 和 UDP 你平时打开网页、调接口（HTTP/1.1、HTTP/2）走的是 TCP。较新的 HTTP/3 则改用基于 UDP 的 QUIC 协议，在 UDP 之上自己实现了序号、确认、重传，好处是能更快建立连接、一个包丢了不会拖住其他请求。视频会议用的 WebRTC 也主要走 UDP——和 Skype 一个道理。
第 4 节

DNS：互联网的电话簿

你的计算机想连接一个网站时，需要两样东西：一个 IP 地址和一个端口。比如 172.217.7.238 的 80 号端口，这是谷歌网页服务器的 IP 地址和端口。事实上，你可以把它输进浏览器的地址栏，就会来到谷歌首页。这样能到达正确的目的地，但要记住那一长串数字实在太烦了。google.com 好记多了。

所以互联网有一个专门的服务，负责把这些域名对应到地址上。它就像互联网的电话簿，叫域名系统（Domain Name System），简称 DNS。它的工作方式你大概能猜到：你在浏览器里输入 "youtube.com" 这样的名字，浏览器就去问一台 DNS 服务器——通常是你的 ISP 提供的——请它查一下地址。DNS 查它那本巨大的登记簿，回复对应的地址……如果有的话。

事实上，如果你在键盘上乱敲一通，加上 ".com"，然后在浏览器里按回车，很可能会看到一条错误，说 DNS 失败了。这是因为那个网站不存在，DNS 没法给你的浏览器一个地址。但如果 DNS 返回了一个有效的地址——"YouTube.com" 应该会——你的浏览器就会通过 TCP 发出请求，获取网站的数据。

动手：查一个域名

注册的域名有超过 3 亿个（字幕误作"三千万"，英文原文是 300 million），所以为了让 DNS 查询更好管理，它不是存成一个超长的列表，而是存成一种树形数据结构。最顶层叫顶级域名（Top Level Domains，TLD），是 .com、.gov 这样的大类。下面是更低一级的域名，叫二级域名，比如 .com 下面的 google.com 和 dftba.com。再往下还有更低级的域名，叫子域名，比如 images.google.com、store.dftba.com。这棵树绝对是超级巨大！刚才说了，超过 3 亿个域名，这还只是二级域名，不包括所有子域名。因此，这些数据分布在很多台 DNS 服务器上，不同的服务器负责（是权威）树的不同部分。

在 DevTools 里看看 打开浏览器开发者工具的 Network 面板，点任意一个请求，Headers 里的 "Remote Address" 就是 DNS 查出来的 IP 加端口（通常是 :443）；Timing 里的 "DNS Lookup" 是查询花的时间。浏览器和操作系统会把查过的结果缓存一段时间，所以第二次访问往往是 0 毫秒。
第 5 节

OSI 模型：又一层新抽象

好了，我知道你一直在等这句话……我们到了一层新的抽象！

过去两集，我们从电线里的电信号——在无线网络里则是空气中传播的无线电信号——一路讲上来。这叫物理层。MAC 地址、冲突检测、指数退避，以及类似这些协调对物理层访问的底层协议，属于数据链路层。再往上是网络层，我们讨论过的各种交换和路由技术都在这一层工作。今天我们主要讲的是传输层，比如 UDP 和 TCP 这样的协议，负责计算机之间点对点的数据传输，以及尽可能地检测和修复错误。我们还稍微碰到了会话层：在这一层，TCP 和 UDP 这样的协议被用来打开一个连接、来回传递信息、结束后关闭连接——这叫一次会话（session）。你做 DNS 查询或者请求一个网页时，发生的正是这件事。

6表示层HTML 解码、视频流下一集

这些是开放式系统互联（Open System Interconnection，OSI）模型的下面五层。OSI 是一个概念框架，用来把这些不同的网络过程分门别类。每一层关心和解决的问题都不一样；要是想一口气造出一个巨大的、不分层的网络实现，是不可能的。正如整个系列一直在说的，抽象让计算机科学家和工程师能同时改进技术栈的各个层次，而不被全部的复杂度压垮。

而且神奇的是，我们还没讲完！OSI 模型还有两层：表示层和应用层，包括网页浏览器、Skype、HTML 解码、在线看电影等等。我们下周讲。到时见！

第 6 节

本集小结

协议 / 服务解决什么要点
IP送到哪台电脑头部基本只有目的地址；很底层
UDP送到哪个程序端口号 + 校验和；不修复、不确认；简单快速（Skype 视频）
TCP一个都不能少序号（排序、去重）、ACK、超时重发、多包并发、拥塞控制；代价是确认包让消息翻倍
DNS名字 → 地址互联网的电话簿；树形结构：顶级域名 → 二级域名 → 子域名，分布在很多服务器上
OSI把网络分层物理、数据链路、网络、传输、会话、表示、应用
一句话 数据包像套娃：最外层 IP 头部把它送到对的电脑，里面一层 UDP / TCP 头部的端口号把它交给对的程序；TCP 再靠序号和确认保证不丢、不乱、不重。DNS 先把好记的域名翻译成 IP 地址。每一层只管自己的事，这就是 OSI 分层的意义。

合上页面，试着回答

1. 既然 IP 包已经能送到正确的电脑，为什么还需要 UDP 的端口号？
IP 头部基本只有目的地址，包到了电脑，操作系统不知道该交给哪个程序。每个联网程序都向操作系统申请一个唯一端口，操作系统读 UDP 头部里的端口号，就知道交给谁（比如 3478 交给 Skype）。
2. 数据 89、111、33、32、58、41 的校验和是多少？接收方怎么用它？
364。接收方把收到的数据重新加一遍，和头部里的校验和比较：一样就正常，不一样说明数据在途中损坏了。UDP 只会把坏包扔掉，不会请求重发。
3. TCP 发出一个包后没等到 ACK，会怎么做？如果其实包已经到了、只是 ACK 丢了，会不会出问题？
等够一定时间后重发同一个包。不会出问题：接收方靠序号认出这是重复的包，直接丢掉。
4. 输入 youtube.com 回车后，浏览器先做什么？DNS 为什么存成树而不是一张大表？
先问 DNS 服务器（通常是 ISP 提供的）这个域名对应的 IP 地址，拿到后再通过 TCP 向这个地址请求网页数据；查不到就报 DNS 错误。域名有 3 亿多个（还不算子域名），按顶级域名、二级域名、子域名组织成树，就能把不同部分分给不同的 DNS 服务器负责。
