引用和内存

References, pass by value, stack frames and the heap

把一张工单交给方法处理：方法先修改它的状态，又把参数换成一张新工单。回到调用处，手里拿到的究竟是哪一张？沿着变量与对象之间的箭头走一遍，就能分清“修改对象”和“替换引用”，也能看懂复制、返回值与空指针为什么会出现这些结果。

一张工单，两种修改→画出引用→跟进方法调用→复制与空值

本篇以 Java 8 为准。示例只用 JDK，不依赖 Spring、数据库或其他篇的代码。

第 1 节

方法到底改了什么？

先用一个很小的类表示工单：WorkOrder 只有一个整数状态 status。本篇约定 0 表示待受理，1 表示已受理，9 表示已归档；这些数字只是实验数据。new WorkOrder(0) 创建一张状态为 0 的工单。

下面是一段完整程序。main 创建工单，然后调用 process。先别运行，看看最后两行会打印什么：status 是 0、1 还是 9？attempts 是 0 还是 1？

三次赋值，哪些能影响调用方？

public class ReferencePuzzle {
    static class WorkOrder {
        int status;

        WorkOrder(int status) {
            this.status = status;
        }
    }

    static void process(WorkOrder order, int attempts) {
        order.status = 1;
        order = new WorkOrder(9);
        attempts++;
    }

    public static void main(String[] args) {
        WorkOrder order = new WorkOrder(0);
        int attempts = 0;
        process(order, attempts);
        System.out.println("status=" + order.status);
        System.out.println("attempts=" + attempts);
    }
}
status=1
attempts=0

调用方看见了状态 1，却没拿到状态 9 的新工单，尝试次数也仍是 0。三个赋值都执行过，区别在于它们各自改的是对象里的字段，还是方法自己的参数变量。

代码中的 static class WorkOrder 是放在实验程序里的一个小类；这样可以把示例写在一起。它的构造器 WorkOrder(int status) 在创建对象时接收初始状态，this.status = status 把参数写进这个对象的字段。读这个实验时，只需认出“创建工单”和“修改状态”两件事。

第 2 节

变量里放的是引用

先把方法调用拿开，只看一次赋值。WorkOrder first = new WorkOrder(0) 创建了对象，也声明了一个变量。对象保存 status，变量 first 保存的是指向该对象的引用值。为了画图，把这个对象叫作 A；A 只是我们取的图中编号，不是程序读出的内存地址。

接着写 WorkOrder second = first，复制的是 first 里那个引用值。没有再次执行 new，也没有复制工单的字段。现在有两个变量，都能找到同一张工单。

试着顺着 second 修改状态，再把 second 改指向另一张工单。运行前判断：哪一步之后，first 和 second 不再指向同一个对象？以下片段放在 main 中，使用开篇相同的 WorkOrder 定义。

WorkOrder first = new WorkOrder(0);
WorkOrder second = first;
System.out.println("sameBefore=" + (first == second));
second.status = 1;
System.out.println("firstStatus=" + first.status);
second = new WorkOrder(9);
System.out.println("sameAfter=" + (first == second));
System.out.println("secondStatus=" + second.status);
sameBefore=true
firstStatus=1
sameAfter=false
secondStatus=9

second.status = 1 先沿着 second 找到 A，再改 A 的字段。first 仍指向 A，因此它读到的也是 1。second = new WorkOrder(9) 则先创建对象 B，再把 second 保存的引用换成 B 的引用；这一步没有给 first 赋值，first 仍指向 A。

对这里两个 WorkOrder 引用使用 ==，比较的是是否指向同一个对象。两个对象即使字段完全相同，也不会因此成为同一个对象；这是对象身份与字段内容的区别。两个 null 引用也会比较为 true，但 null 不对应任何对象。

读赋值时先看左边：second.status = … 写入对象的字段；second = … 写入变量本身。沿箭头修改对象，和改画一条箭头，是两个动作。
第 3 节

参数怎样进入方法？

回到开篇的 process(order, attempts)。调用时，Java 先求出实参的值，再用这些值初始化这次调用的新参数变量。对 int 而言，复制的是整数 0；对 WorkOrder 而言，复制的是指向 A 的引用值。

调用处的 order 与方法参数 order 恰好同名，但它们是两个变量。你可以把方法里的那个改名为 incoming，行为不变。下面逐步执行这次调用，重点观察：A 的状态何时改变？哪一条箭头改指向了 B？

跟着一次调用走

引用关系示意。省略与本例无关的参数及 JVM 内部数据，不表示物理地址。

  1. // main：order → A，attempts = 0
  2. process(order, attempts); // 复制实参值
  3. order.status = 1;
  4. order = new WorkOrder(9);
  5. attempts++;
  6. // process 返回，继续 main
0 / 5

main 已创建工单 A，状态为 0。现在准备调用 process，main 的 attempts 也是 0。

进入方法时，两个 order 都指向 A。所以第一句 order.status = 1 修改了共同可见的工单。第二句给参数 order 赋了新值：参数改指向 B，main 的 order 仍指向 A。第三句只增加参数 attempts，main 的 attempts 仍是自己的 0。方法返回时，main 因而读到 status=1 和 attempts=0。

这就是 Java 的值传递。引用值也属于“值”，它让两个变量能访问同一对象；它不让被调用方法直接改写调用方的局部变量。只记“对象传进去能改”，容易漏掉重新赋值这一步的差别。

判断一次调用会不会改变已有对象，要去看方法做了什么。参数类型是 WorkOrder，只说明它能接收这种引用；单凭类型，无法知道方法会修改字段、创建新对象，还是只读取数据。
第 4 节

栈帧结束，对象还在吗？

刚才图左边的两块区域，就是理解方法调用用的栈帧模型。说得直白些：每次方法调用，JVM 都给这次调用单独开一块“草稿区”，参数和方法里的局部变量放在里面；方法返回，这块草稿区就收走。每个线程有自己独立的一摞草稿区（术语叫虚拟机栈），所以两个线程同时调用同一个方法，各自的参数互不相干。规范里这块草稿区叫帧，除了局部变量，还放一些计算的中间结果。

图右边是堆，对象住的地方。所有线程共用这一个堆，new 出来的对象和数组都从这里分配。这里有个容易混的点：工单的 status 虽然是 int，但它是对象的字段，跟着对象住在堆上，而不是住在某个栈帧里。所以“基本类型都在栈上、引用类型都在堆上”这句话不对——它把变量的类型和变量所在的位置混为一谈了。变量里放的是引用还是整数，跟这个变量本身住在哪，是两回事。

这里画的是规范层面的逻辑关系，不是内存快照。JVMS 允许不同实现采用不同布局，甚至允许帧在堆上分配；实际执行还可能优化掉分配。不能凭这张图推算地址、大小，或断言每个 new 最终都有一块独立的物理内存。

返回的是引用，对象不随局部变量消失

如果方法结束就必须销毁它创建的对象，那工厂方法便无法工作。看下面的 create：它创建工单，再把引用返回。调用方接住这个引用后，仍然能访问那张工单。方法内的变量结束了，对象依然能被后续代码使用。

static WorkOrder create() {
    WorkOrder order = new WorkOrder(0);
    return order;
}

static WorkOrder replace(WorkOrder order) {
    order = new WorkOrder(9);
    return order;
}

replace 也返回了一个新对象。比较以下两种调用：第一次忽略返回值；第二次把返回值赋给调用方的 order。使用相同的 WorkOrder 定义，在 main 中运行：

WorkOrder order = create();
replace(order);
System.out.println("ignored=" + order.status);
order = replace(order);
System.out.println("received=" + order.status);
ignored=0
received=9

第二次之所以拿到新工单，是因为调用方执行了 order = …。赋值右边的方法调用先完成，返回新工单的引用，再把这个引用写进调用方的变量。方法内部的参数赋值和调用方的接收赋值，各自发生在自己的变量上。

对象什么时候才有机会被回收？

看的是对象还能否被程序的后续计算访问，而不只是“创建它的方法结束了吗”。从还在使用的变量、静态字段等出发，沿着对象字段、数组元素中的引用，可能继续找到其他对象。只要对象还通过这样的路径被保留，就不能仅因某个局部变量消失而认定它可以回收。

在这里的简化模型中，如果所有通往某个对象的路径都断了，它就可能成为垃圾回收的对象。两个对象互相引用，也不意味着一定能存活：如果运行中的程序已经无法到达它们，这个环本身不会把它们保留下来。反过来，把对象放进一个长期可访问的集合，哪怕业务上早已不用它，只要引用还留着，它仍可能被保留。

“不再可达”和“已释放内存”不是同一个时刻。图中 process 返回后不再画出通向 B 的箭头，只是在说明本例的引用关系；图没有观测垃圾回收，也没有证明 B 当时已被回收。我们无需主动销毁对象，但要留意长期对象是否还持有不需要的引用。

第 5 节

复制了数组，为什么工单还会一起变？

现在有一个工单数组，想复制一份再调整其中的状态。数组自身也是对象；WorkOrder[] 的每个元素保存一个工单引用。调用数组的 clone() 会创建新数组，并复制各个元素的值。

先预测下面的两次修改：copy[0].status = 1 与 copy[0] = new WorkOrder(9)，哪一次会影响通过 original 读到的工单状态？这里仍使用开篇的 WorkOrder。

WorkOrder[] original = { new WorkOrder(0) };
WorkOrder[] copy = original.clone();
System.out.println("sameArray=" + (original == copy));
System.out.println("sameElement=" + (original[0] == copy[0]));
copy[0].status = 1;
System.out.println("originalStatus=" + original[0].status);
copy[0] = new WorkOrder(9);
System.out.println("originalAfterReplace=" + original[0].status);
System.out.println("copyStatus=" + copy[0].status);
sameArray=false
sameElement=true
originalStatus=1
originalAfterReplace=1
copyStatus=9

original → 数组 X → [0] → 工单 A

copy     → 数组 Y → [0] → 工单 A

clone 刚完成时的示意：X 与 Y 是两个数组，里面的第 0 个元素却指向同一张工单。

sameArray=false 证明数组本身已经分开；sameElement=true 则说明工单没有分开。沿着 copy[0] 改状态，改的是共同的 A，所以 original[0] 也能读到 1。随后给 copy[0] 赋值，改的是数组 Y 的那个元素；数组 X 的元素没变，它仍指向 A。

这种只复制一层、嵌套对象仍共享的复制叫浅拷贝。要让这份示例中的工单独立，需要再创建 WorkOrder，并把状态值复制进去。如果工单还包含可变的联系人、明细列表等对象，就要继续判断哪些也应该复制。深拷贝的关键是需要独立的对象是否真的分开了，不能只数外面写了几次 new。

读到 DTO 转换或 Bean 复制工具时，也用这个问题检查它：复制了字段值以后，引用类型字段还指向原对象吗？具体要查所用工具及该字段的处理逻辑；不能仅凭方法名里有 copy 就认定它做了深拷贝。
第 6 节

null 在哪一步出错？

null 是一种引用值，表示它没有指向任何对象。它不是空白工单，也不会自动创建一个对象。给变量赋 null、把 null 传入方法，或者与 null 比较，本身都不要求访问某个对象；真正沿着它访问实例字段、调用实例方法时，才会遇到空指针问题。

先试一个容易混淆的操作。在第 4 节运行完的 main 中，order 指向状态为 9 的工单。把这份引用赋给 alias，再清空 order。alias 还能访问工单吗？

WorkOrder alias = order;
order = null;
System.out.println("aliasStatus=" + alias.status);
System.out.println("orderIsNull=" + (order == null));
aliasStatus=9
orderIsNull=true

能。order = null 只清空 order 自己的引用，没有给 alias 赋值，也没有销毁它们原来共同指向的对象。对某个变量赋 null，不等于把所有别名一并清空。

字段有默认值，局部变量仍需先赋值

再给工单加一个派单人编号。Integer 是 int 对应的包装类，是引用类型；它可以表达一个整数，也可以为 null。本例把 null 约定为“尚未派单”，这层业务含义由我们规定，Java 只负责表示空引用。

static class WorkOrder {
    int status;
    Integer assigneeId;
}

这个类没有显式写构造器，可以用自动提供的无参构造器创建对象。先读两个字段，再创建两个长度为 1 的数组：

WorkOrder order = new WorkOrder();
System.out.println("statusDefault=" + order.status);
System.out.println("assigneeDefault=" + order.assigneeId);

int[] counts = new int[1];
WorkOrder[] orders = new WorkOrder[1];
System.out.println("countElement=" + counts[0]);
System.out.println("orderElement=" + orders[0]);
statusDefault=0
assigneeDefault=null
countElement=0
orderElement=null

新对象的 int 字段默认是 0，引用类型字段默认是 null；新数组的元素也按类型取默认值。new WorkOrder[1] 只创建了数组，没有创建里面的工单，所以直接访问 orders[0].status 会遇到 null。

这个默认初始化规则不意味着可以读取未赋值的局部变量。方法里声明 Object order; 后直接读取 order，会在编译阶段被拒绝：编译器必须能确定，读取前该局部变量已经赋过值。“没有赋值”和“已经赋值为 null”是两回事。

一行没写点号的代码，也可能需要对象

拿上面的 order 继续运行。int id = order.assigneeId 看起来只是赋值；但左边需要 int，右边是 Integer，Java 需要把包装对象拆箱为整数。assigneeId 为 null 时，没有对象能提供这个整数，于是抛出 NullPointerException。

try {
    int id = order.assigneeId;
    System.out.println(id);
} catch (NullPointerException e) {
    System.out.println("unbox=" + e.getClass().getSimpleName());
}

WorkOrder missing = null;
try {
    System.out.println(missing.status);
} catch (NullPointerException e) {
    System.out.println("field=" + e.getClass().getSimpleName());
}
unbox=NullPointerException
field=NullPointerException

这里用 try/catch 把两次失败的异常名称打印出来，便于继续实验。第一处，工单对象存在，空的是它的 assigneeId 字段；第二处，missing 本身就是空引用，读取实例字段便失败。排查时要逐步看表达式访问了哪个对象，而不只看整行里有没有一个变量非空。

如果“没有工单”或“尚未派单”本来就是允许的状态，应在使用字段之前处理这个分支。反之，如果方法要求必须有工单，就在入口明确拒绝 null。把缺失值随手改为 0，虽然可能避开拆箱异常，却也可能把“尚未派单”改成了“派给编号 0”；是否能这样做，要由业务约定决定。

第 7 节

返回一张独立的工单

把这些规则用到一个明确的小需求里：给一张工单指定派单人，保留输入工单的原有内容，返回修改后的新工单。本例只保留状态和派单人编号两个字段，允许原工单尚未派单；如果工单本身不存在，就抛出带说明的 IllegalArgumentException。

先找三个位置：在哪里创建新对象，在哪里写入派单人，在哪里接住返回值。也可以先判断：运行后原工单的派单人是 null 还是 7？

public class ReassignOrder {
    static class WorkOrder {
        int status;
        Integer assigneeId;

        WorkOrder(int status, Integer assigneeId) {
            this.status = status;
            this.assigneeId = assigneeId;
        }
    }

    static WorkOrder assignCopy(WorkOrder source, int assigneeId) {
        if (source == null) {
            throw new IllegalArgumentException("工单不存在");
        }
        WorkOrder copy = new WorkOrder(source.status, source.assigneeId);
        copy.assigneeId = assigneeId;
        return copy;
    }

    public static void main(String[] args) {
        WorkOrder source = new WorkOrder(0, null);
        WorkOrder assigned = assignCopy(source, 7);
        System.out.println("sameObject=" + (source == assigned));
        System.out.println("sourceAssignee=" + source.assigneeId);
        System.out.println("assignedAssignee=" + assigned.assigneeId);
        try {
            assignCopy(null, 7);
        } catch (IllegalArgumentException e) {
            System.out.println("rejected=" + e.getMessage());
        }
    }
}
sameObject=false
sourceAssignee=null
assignedAssignee=7
rejected=工单不存在

这次 copy.assigneeId = assigneeId 修改的是刚创建的对象，source 指向的原对象没有被修改。方法把新对象的引用返回，main 把它接在 assigned 中。于是两张工单身份不同，派单人也可以不同。

复制构造时，status 复制整数值，assigneeId 复制 Integer 引用值。这里共享 Integer 不会让一个编号对象被原地改写，因为 Integer 的整数值不可变；后面的赋值是在替换新工单的字段。如果字段换成可变的联系人或数组，就需要重新检查共享范围，不能照搬“复制两个字段便完成”的结论。

这是对象关系实验，工单状态、编号与空值含义均为本篇设定。程序没有连接数据库；内存中修改对象，不代表任何数据库记录已被更新。

第 8 节

小结和自测

带走一句话赋值和传参会复制值；值若是引用，两个变量便能找到同一个对象。沿引用改字段会改变这个对象，给变量重新赋值只会改变该变量保存的引用。
代码中的动作追踪哪一处变化
other = order复制引用，尚未复制工单。
other.status = 1沿 other 找到工单，再写入它的字段。
other = new WorkOrder(9)创建新工单，并替换 other 的引用。
order = replace(order)方法先返回引用，调用方再把它赋给 order。
other = null清空 other，不会清空别名或立即销毁对象。

试着在心里画出箭头

1. 把开篇 process 里的两句调换：先给参数 order 赋一张新工单，再修改它的 status。调用方原工单的状态还会变吗？
不会，仍是 0。参数先改指向新对象，后续字段修改便落在新对象上。main 的 order 从始至终指向原对象 A。这说明不能只看方法里“有没有改字段”，还要追踪改字段时参数指向谁。
2. 数组 clone 后，给 copy[0] 赋 null，original[0] 会不会也变成 null？
不会。两个数组是不同对象，各自拥有独立的第 0 个元素。赋 null 只改变 copy 数组中的元素。浅拷贝共享的是元素原来指向的工单，不是两个数组的元素位置。
3. 方法创建了工单并返回引用。方法栈帧结束后，调用方为什么还能使用工单？
栈帧里结束的是这次调用的局部变量等数据。调用方已经接住返回的引用，对象仍可被后续代码访问；局部变量的生命周期不能直接当成对象的生命周期。
4. 已确认 order != null，能保证 int id = order.assigneeId 不抛空指针异常吗？
不能。order 存在只保证能读取它的字段；Integer 字段 assigneeId 仍可能为 null。赋给 int 时发生拆箱，null 无法拆成整数。
5. 两个工单互相引用，但程序已经无法从其他仍可访问的位置找到它们。仅凭这两条相互引用，能阻止垃圾回收吗？
不能。互相引用并不等于程序还能到达它们。在本篇讨论的普通引用模型中，如果这个环已不可达，它可以被回收；至于何时实际回收，不能凭引用图确定。

参考资料

语言与虚拟机规则按 Java SE 8 文档核对，核对日期为 2026-11-16。下面分别列出引用的依据与它支撑的结论。

Java 语言规范（Java SE 8）

  • JLS §8.4.1：形式参数；§4.12.3：变量的种类支撑：第 3 节：调用时用实参的值初始化新建的参数变量（值传递）；每次调用都新建参数变量，方法体执行结束它就不再存在。
  • JLS §4.3.1：对象支撑：第 2、6 节：引用是指向对象的指针，null 是不指向任何对象的特殊引用。
  • JLS §4.12.5：变量的初始值支撑：第 6 节：int 字段与数组元素默认 0，引用类型默认 null；局部变量使用前必须显式赋值。
  • JLS §15.21.3：引用相等运算符 == 和 !=支撑：第 2 节：== 比较是否指向同一个对象，两个 null 也比较为 true。
  • JLS §15.11.1：用主表达式访问字段支撑：第 6 节：沿值为 null 的引用读取实例字段，抛 NullPointerException。
  • JLS §5.1.8：拆箱转换支撑：第 6 节：对 null 做拆箱抛 NullPointerException。
  • JLS §10.7：数组的成员支撑：第 5 节：数组的 clone 返回同类型的新数组；多维数组的克隆是浅的，子数组被共享。
  • JLS §16：明确赋值支撑：第 6 节：局部变量在被读取前必须已明确赋值，否则编译报错。
  • JLS §12.6.1：实现终结支撑：第 4 节：互相引用的一组对象若整体变得不可达，它们的存储可以被回收。

Java 虚拟机规范（Java SE 8）

  • JVMS §2.5.2：虚拟机栈；§2.6：帧支撑：第 4 节：每个线程有自己的私有栈，方法调用压入帧，帧存放局部变量和部分结果；规范也允许帧在堆上分配。
  • JVMS §2.5.3：堆支撑：第 4 节：堆由所有线程共享，类实例和数组的内存从堆分配，由垃圾回收器自动回收。

官方 API 文档

  • Object：clone()支撑：第 5 节：逐字段“如同赋值”地复制，字段内容本身不再克隆，因此是浅拷贝；所有数组都视为实现 Cloneable。
  • Integer支撑：第 7 节：Integer 只包装一个 int 值，提供的方法都是读取、转换和比较，没有改写这个值的办法。
