String：不可变、常量池、== 和 equals

Immutability, the string pool, == and equals

两个内容一模一样的字符串，== 有时说相等，有时说不相等。差别不在内容，而在两个变量指向的是不是同一个对象。这一篇用几段在 JDK 8 上实际运行过的小程序，看清字符串对象从哪里来、常量池登记了什么、String 为什么设计成不可变，以及比较内容时该用谁。

先猜→身份与内容→字符串工作台→拼接的两副面孔→不可变与它的代价

本篇以 Java 8 为准。示例只用 JDK，不依赖 Spring、数据库或其他篇的代码；“运行”展示的是预先用 JDK 8 执行并记录的结果。

第 1 节

先猜：内容一样，== 就说相等吗？

下面是一个完整的小程序。它造了三个内容都是 notice 的字符串，又写了一个由两段字面量拼出来的 "no" + "tice"，然后做四次比较。先别运行，凭直觉猜三件事。

public class ComparePuzzle {
    public static void main(String[] args) {
        String a = "notice";
        String b = "notice";
        String c = new String("notice");
        System.out.println("a==b=" + (a == b));
        System.out.println("a==c=" + (a == c));
        System.out.println("a.equals(c)=" + a.equals(c));
        System.out.println("fold==a=" + ("no" + "tice" == a));
    }
}
① 两个字面量：a == b 是 true 还是 false？
true。内容相同的字面量共用同一个对象，a 和 b 指向它。为什么能共用，第 3 节讲。
② new 出来的 c：a == c 和 a.equals(c) 各是什么？
== 是 false，equals 是 true。new String("notice") 创建了一个新对象：内容相同，身份不同。两个比较器问的根本不是同一个问题，第 2 节拆开看。
③ 拼出来的："no" + "tice" == a 是 true 还是 false？
true。两段字面量相加，编译器在编译期就把结果算成了 "notice"，根本没有发生运行时的拼接。但把其中一段换成变量，结果就反过来——第 4 节用字节码看这个差别。

a==b=true
a==c=false
a.equals(c)=true
fold==a=true

四行输出对应四个比较。三个字符串内容完全一样，== 却给出了两种答案；而 equals 说它们相等。要解释这个分裂，得先弄清这两个运算符各自在比较什么。

第 2 节

== 问身份，equals 问内容

Java 里的字符串不是基本类型，String 是一个类，字符串变量里放的是指向对象的引用——字面量也不例外，语言规范明确说“字符串字面量是 String 类实例的引用”。所以 a == c 比较的不是字符，而是两个引用是否指向同一个对象；规范把这叫对象相等（object equality）。c 是 new 出来的另一个对象，哪怕字符一个不差，== 也是 false。

equals 问的是另一个问题。String 重写了这个方法，它的契约是：参数不为 null、也是 String、且表示相同的字符序列时才返回 true。它不关心两个对象是不是同一个。所以 a.equals(c) 是 true。

如果你写过 JavaScript：那里两个字符串用 === 比较的就是内容；Java 的 == 对对象比较的是身份。这是本节大多数反直觉结果的根源。

比较两个字符串的内容，用 equals，不用 ==。== 偶尔给出 true（比如两个字面量之间），只是碰巧它们共用一个对象，不能依赖。

一个常见的配套写法：把确定不为 null 的一方放在前面，"notice".equals(input)。input 是 null 时，equals 的契约保证返回 false；反过来写 input.equals("notice")，input 为 null 就会抛 NullPointerException——沿着空引用调用方法，方法根本没机会执行。

第 3 节

常量池：字面量都登记在册

回到第 1 节的 a == b 为什么是 true。语言规范规定：字符串字面量总是指向 String 的同一个实例——字面量，以及更一般的“常量表达式的值”，都会被 intern（登记），以便共享唯一的实例。类加载时，JVM 为遇到的字面量创建 String 对象；如果同样的内容已经登记过，就不再创建。

这个登记处叫字符串常量池，由 String 类自己维护，起初是空的。内容相同的字面量在池里只有一个对象，谁写这个字面量，谁的变量就指向它。而 new String("notice") 是明确的“创建新对象”指令：即使内容已在池里，也照样新建一个。这就是 a 和 c 身份不同的原因。

运行时拼接也产生新对象：规范说，字符串拼接的结果是新创建的 String，除非整个表达式是常量表达式（第 4 节细说）。所以 part + "tice" 每次执行都造一个新对象。

e 的那一步值得单独说。intern() 的契约是：池里已经有内容相等（按 equals 判断）的字符串，就返回池里那个；没有，就把这个对象本身登记进池，并返回它自己。d 的内容是 notice，池里早有 a 登记的那个，所以 d.intern() 返回的是 a 指向的对象，a == e 是 true，而 d 自己仍指向堆里那个拼接产物。

反过来，如果内容从没登记过呢？下面程序的最后两行在运行时拼出内容 blade——它不以字面量形式出现在程序里，池里起初没有它——然后 intern。先猜：fresh.intern() == fresh 是 true 还是 false？

public class PoolLab {
    public static void main(String[] args) {
        String a = "notice";
        String b = "notice";
        String c = new String("notice");
        String part = "no";
        String d = part + "tice";
        String e = d.intern();
        System.out.println("a==b=" + (a == b));
        System.out.println("a==c=" + (a == c));
        System.out.println("a==d=" + (a == d));
        System.out.println("a==e=" + (a == e));
        System.out.println("c==d=" + (c == d));
        System.out.println("d==e=" + (d == e));
        System.out.println("a.equals(d)=" + a.equals(d));
        System.out.println("c.intern()==a=" + (c.intern() == a));
        String fresh = new StringBuilder("bla").append("de").toString();
        System.out.println("fresh.intern()==fresh=" + (fresh.intern() == fresh));
    }
}
a==b=true
a==c=false
a==d=false
a==e=true
c==d=false
d==e=false
a.equals(d)=true
c.intern()==a=true
fresh.intern()==fresh=true

最后一行是 true：池里没有 blade，intern 把 fresh 自己登记了进去，返回的就是它。所以“intern 返回池里的对象”要补上半句——池里没有时，登记的正是你这个对象。这也是为什么 s.intern() == t.intern() 与 s.equals(t) 永远同真同假：intern 之后，内容相同的字符串必然指向同一个登记对象。

第 4 节

拼接：编译期算好的，和运行时才拼的

第 1 节埋了一个反差："no" + "tice" == a 是 true，part + "tice" == a 是 false。两行看起来做的是同一件事，结果为什么相反？再加一行：把变量声明成 final，结果又会变。先猜第三行。

public class FoldLab {
    public static void main(String[] args) {
        String a = "notice";
        String part = "no";
        final String fixed = "no";
        String r1 = "no" + "tice";
        String r2 = part + "tice";
        String r3 = fixed + "tice";
        System.out.println("r1==a=" + (r1 == a));
        System.out.println("r2==a=" + (r2 == a));
        System.out.println("r3==a=" + (r3 == a));
    }
}
r1==a=true
r2==a=false
r3==a=true

关键在常量表达式这个概念。规范列出了它的组成：字面量、加减等运算符、以及指向“常量变量”的名字——而常量变量是用常量表达式初始化的 final 基本类型或 String 变量。于是：

  • "no" + "tice"：两个字符串字面量相加，是常量表达式。编译器直接算出 "notice"，并且规范规定 String 常量表达式的值同样被 intern——它和 a 指向同一个登记对象。
  • part + "tice"：part 不是 final，编译期不知道它的值，整个表达式不是常量表达式。运行时才拼接，产生新对象。
  • fixed + "tice"：fixed 是 final 且用字面量初始化，是常量变量，它的名字可以出现在常量表达式里。于是这一行也在编译期算成了 "notice"。

完整反汇编输出保存在实验记录里（javap/FoldLab.txt）。

ldc 的意思是“从常量池取一个现成的常量”。r1（偏移 6）和 r3（偏移 31）都是直接 ldc 编号 #2 的 "notice"——和 a 的赋值（偏移 0）取的是同一个常量，指令里没有任何拼接动作。r2（偏移 10–29）则是现场 new 一个 StringBuilder，append 两次，再 toString 出一个新 String。编译期折叠与运行时拼接的差别，在指令层面一目了然。

顺带说明：规范允许编译器用缓冲类来减少拼接产生的中间对象，JDK 8 的 javac 实际用的是 StringBuilder——上面偏移 10 的指令就是证据。单个表达式里的多次 + 会被这样优化成一次构建，第 6 节会看到循环里的 += 享受不到这个优化。

第 5 节

不可变：方法从不修改原字符串

String 的官方文档第一句就声明：字符串是常量，创建之后值不能改变。看一个容易误会的实验：s.toUpperCase() 和 s.trim() 之后，s 自己变了吗？先猜，再运行。

public class ImmutableLab {
    public static void main(String[] args) {
        String s = " Notice ";
        String upper = s.toUpperCase();
        String trimmed = s.trim();
        System.out.println("s=[" + s + "]");
        System.out.println("upper=[" + upper + "]");
        System.out.println("trimmed=[" + trimmed + "]");
        System.out.println("upper==s=" + (upper == s));
        System.out.println("trimmed==s=" + (trimmed == s));
        String clean = "notice";
        System.out.println("clean.trim()==clean=" + (clean.trim() == clean));
        System.out.println("clean.substring(0)==clean=" + (clean.substring(0) == clean));
        String shout = "NOTICE";
        System.out.println("shout.toUpperCase()==shout=" + (shout.toUpperCase() == shout));
        System.out.println("clean.replace('x','y')==clean=" + (clean.replace('x', 'y') == clean));
    }
}
s=[ Notice ]
upper=[ NOTICE ]
trimmed=[Notice]
upper==s=false
trimmed==s=false
clean.trim()==clean=true
clean.substring(0)==clean=true
shout.toUpperCase()==shout=true
clean.replace('x','y')==clean=true

前五行：s 原封不动，还是 " Notice "；大写版和去空白版都是新对象，要用变量接住返回值才能拿到它们。写 s.trim(); 然后继续用 s，等于什么都没做。

后四行是另一半故事，也是容易记错的地方：“每个方法都返回新对象”并不对。当结果的内容和原来完全一样时，这几个方法会直接返回原对象：没有首尾空白可去的 trim、从头取到尾的 substring(0)、没有小写可转的 toUpperCase、找不到目标字符的 replace。trim 的文档写明了这一点，其余几个可以在 JDK 源码里逐行核对（出处见参考资料）。准确的说法是：原对象绝不改变；方法返回的可能是新对象，也可能是原对象自己。所以别用 == 去判断“方法有没有生效”，该比较内容还是比较内容。

源码里长什么样

JDK 自带源码压缩包 src.zip，里面 java/lang/String.java（Corretto 1.8.0_512）第 114 行是字符串的本体：

    private final char value[];

出处：JDK 8 src.zip 内 java/lang/String.java 第 114 行

一个 private 的字符数组，外面拿不到；整个类没有提供修改它内容的方法。本篇核对过的几个“修改”方法，需要改动时都是复制出新数组再包成新 String——比如 concat（第 2026–2034 行）先 Arrays.copyOf 再 new String(buf, true)，replace（第 2066–2091 行）同样新建数组。原对象的数组从不被写入。

不可变换来的一件事：哈希可以缓存

String 还有一个私有字段 hash（第 117 行），默认 0。第一次调用 hashCode() 时按公式算出哈希并存进去，以后直接返回缓存。用反射（运行时读取私有字段的手段，这里只用来观察）可以直接看到这个过程：

import java.lang.reflect.Field;

public class HashLab {
    public static void main(String[] args) throws Exception {
        String s = new String("notice");
        Field hashField = String.class.getDeclaredField("hash");
        hashField.setAccessible(true);
        System.out.println("hashBefore=" + hashField.getInt(s));
        System.out.println("hashCode=" + s.hashCode());
        System.out.println("hashCodeAgain=" + s.hashCode());
        System.out.println("hashAfter=" + hashField.getInt(s));
    }
}
hashBefore=0
hashCode=-1039690024
hashCodeAgain=-1039690024
hashAfter=-1039690024

调用前字段是 0，调用后变成了算出的值。这个缓存成立的前提正是不可变：内容永远不变，算一次就够了。哈希公式本身写在 hashCode 的文档里：s[0]*31^(n-1) + s[1]*31^(n-2) + … + s[n-1]。

为什么后端要在意不可变

把前面的事实连起来，不可变不是洁癖，是三件实际事情的前提：

  • 共享才安全。常量池让 a、b 共用一个对象；如果字符串能被原地修改，a 调一次 toUpperCase 就会把 b 的值也改掉。文档原话是“因为 String 对象不可变，它们可以被共享”。同理，一个字符串在多个线程之间传递，不需要为它的内容加锁。
  • 才能放心当 Map 的键。HashMap 按哈希把键分散到桶里来定位；如果键的内容放进 Map 之后还能变，哈希跟着变，就再也找不到当初放的位置。Map 的文档专门警告：可变对象作键时，若对象在作为键期间发生了影响 equals 比较的改变，Map 的行为未定义。String 不可变，加上哈希缓存，做键既安全又快。
  • 方法签名即承诺。把一个字符串传进任何方法，都不必担心它被悄悄改掉——方法最多返回一个新字符串，接不接由调用方决定。
第 6 节

循环里拼接，别用 +=

不可变有一个直接的代价：每次“修改”都要复制。单个表达式里的 + 已经被编译器优化成一次 StringBuilder 构建（第 4 节看过指令），但循环里的 += 是另一回事——每一轮都是一次独立的拼接表达式。把 20000 个 x 拼成一个长串，两种写法各花多少时间？先猜差距是百分之几，还是几个数量级。

public class ConcatCost {
    public static void main(String[] args) {
        int n = 20000;
        long start = System.nanoTime();
        String s = "";
        for (int i = 0; i < n; i++) {
            s += "x";
        }
        long plusDone = System.nanoTime();
        StringBuilder builder = new StringBuilder();
        for (int i = 0; i < n; i++) {
            builder.append("x");
        }
        String t = builder.toString();
        long builderDone = System.nanoTime();
        System.out.println("sameContent=" + s.equals(t));
        System.out.println("length=" + s.length());
        System.out.println("plusMs=" + (plusDone - start) / 1000000);
        System.out.println("builderMs=" + (builderDone - plusDone) / 1000000);
    }
}
sameContent=true
length=20000
plusMs=171
builderMs=0

这是写这一篇的机器上的一次运行：+= 版 171 毫秒，StringBuilder 版不足 1 毫秒（整除后记为 0）。耗时随机器、JIT 预热和运行次数变化，别把数字当常数；但差距的量级来自一个可以推算的事实。

看 javap -c ConcatCost 里循环体的指令（偏移 21–46）：每一轮都 new 一个 StringBuilder，把已有的 s 整个 append 进去，再 append 一个 x，toString 出新串。也就是说第 i 轮要复制已有的 i 个字符。20000 轮下来，复制的字符总数是 0+1+2+…+19999 = 199,990,000，约两亿次字符复制——这是按指令行为做的等差数列求和，不是测量值。而 StringBuilder 版全程只有一个可扩容的缓冲区，append 往末尾写，最后 toString 才复制一次。

循环里拼接字符串，用 StringBuilder 的 append，最后 toString()。单个表达式里的多个 + 不必手动改写，编译器已经优化。
第 7 节

小结和自测

带走一句话字符串的内容创建后绝不改变。== 问“是不是同一个对象”，equals 问“内容是否相同”。字面量和编译期算得出的拼接共用常量池里的登记对象；new 和运行时拼接产生新对象；intern() 返回登记对象，没有登记就登记自己。

五个问题

1. String s = "notice"; String t = new String("notice"); —— s == t、s.equals(t)、t.intern() == s 各是什么？
false、true、true。t 是新对象，身份不同但内容相同；intern 时池里已有字面量 s 登记的 notice，返回的就是 s 指向的那个。
2. String x = "no"; String y = x + "tice"; —— y == "notice" 是 true 吗？把 x 的声明改成 final String x = "no"; 呢？
第一种是 false：x 不是 final，拼接在运行时进行，y 是新对象。改成 final 后是 true：用常量表达式初始化的 final String 是常量变量，x + "tice" 成为常量表达式，编译期折叠成 "notice" 并 intern。
3. 调用 s.trim() 之后，s 自己变了吗？什么情况下 trim 返回的就是原对象？
s 不变。trim 需要去掉首尾空白时返回新字符串；没有首尾空白可去时返回原对象（文档写明）。所以“调了方法没接返回值”等于白调，而“返回的一定是新对象”也不对。
4. 为什么 String 适合做 HashMap 的键？文档对可变对象作键说了什么？
内容不可变，哈希算一次就缓存，键放进 Map 后定位不会失效。Map 文档警告：可变对象作键时，若它在作为键期间发生了影响 equals 比较的改变，Map 的行为未定义。
5. fresh.intern() == fresh 什么时候是 true？本篇的 fresh 为什么是 true？
当 fresh 的内容还没在池里登记过时：intern 把 fresh 本身登记进池并返回它。本篇的 fresh 在运行时拼出 blade，这个内容不以字面量出现在程序里，池里起初没有，所以返回的就是 fresh 自己。若内容已有登记（比如程序里写过 "blade" 字面量），返回的则是池里那个，比较为 false。

规范：Java 语言规范（Java SE 8）

  • JLS §3.10.5：字符串字面量支撑：第 2、3 节：字面量是 String 实例的引用；字面量总是指向同一个实例，字面量与常量表达式的值被 intern 以共享唯一实例。
  • JLS §12.5：创建新的类实例支撑：第 3 节：new 显式创建新对象；类加载时可能为字面量创建 String 对象，若已 intern 过则不再创建。
  • JLS §15.28：常量表达式支撑：第 4 节：常量表达式由字面量、加法等运算符、指向常量变量的名字组成；String 常量表达式的值总是被 intern。
  • JLS §4.12.4：final 变量与常量变量支撑：第 4 节：常量变量是用常量表达式初始化的 final 基本类型或 String 变量。
  • JLS §15.18.1：字符串拼接运算符 +支撑：第 3、4、6 节：拼接结果是新建的 String，除非表达式是常量表达式；允许编译器用 StringBuffer 或类似技术减少中间对象。
  • JLS §15.21.3：引用相等运算符 == 和 !=支撑：第 2 节：两个引用操作数的 == 是对象相等，比较是否指向同一个对象。

官方 API 文档（Java SE 8）

  • java.lang.String支撑：第 5 节：“字符串是常量，创建后值不能改变”“因为不可变所以可以共享”；equals 的契约（非 null、同为 String、字符序列相同）；intern 的契约（池里有则返回池里的，没有则登记自己并返回自己）；hashCode 公式；trim 无首尾空白时返回原对象。
  • java.util.Map支撑：第 5 节：可变对象作键、且在作为键期间发生影响 equals 比较的改变时，Map 的行为未定义。
  • java.util.HashMap支撑：第 5 节：基本操作的常数时间性能以哈希把元素妥善分散到桶里为前提。

工具与源码

  • javap 工具文档支撑：第 4、6 节：javap 反汇编 class 文件，-c 输出各方法的字节码指令。
  • JDK 8 src.zip 内的 java/lang/String.java（Amazon Corretto 1.8.0_512）支撑：第 5 节：value 字段（114 行）、hash 字段（117 行）、hashCode 的缓存逻辑（1465–1476 行）、concat 复制新数组（2026–2034 行）、replace 新建数组（2066–2091 行）、substring(0) 返回 this（1933 行）、trim 返回 this（2878 行）、toUpperCase 无改动返回 this（2748 行）。本机查看：unzip -p "$(/usr/libexec/java_home -v 1.8)/src.zip" java/lang/String.java（macOS、已装 JDK 8）；其他环境解开 JDK 安装目录下的 src.zip 即可。
