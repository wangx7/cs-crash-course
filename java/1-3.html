String：内容一样，对象未必一样

Identity, immutability, and the string pool

两个字符串都装着 blade，写 == 却可能一个 true、一个 false。差别不在字符，而在表达式什么时候求值、对象由谁创建、字面量如何驻留。这一篇用七道判断题把这些路径分开，再落到三件具体工作：判等时躲开 null，循环拼接时读懂 StringBuilder，处理 emoji 时别拿 length() 当字符数。

第 1 节

先猜：七个 blade

先只读声明，不急着记“常量池规则”。a 到 f 的字符内容全都是 blade；c 显式复制了一份，e 用普通变量拼接，f 用 final 常量变量拼接。

String a = "blade";
String b = "blade";
String c = new String("blade");
String d = "bl" + "ade";
String prefix = "bl";
String e = prefix + "ade";
final String fixed = "bl";
String f = fixed + "ade";

逐行选 true 或 false。选完才显示 JDK 8 的实测结果；七行全做完，再看后面的解释。

这些结果不是让你背七行答案，而是把三个问题分开：String 能不能改（第 2 节）、引用是否指同一个对象（第 3 节）、字符内容是否相同（第 4 节）。

第 2 节

不可变：改的是谁

Java 8 的 String API 写得很直接："Strings are constant; their values cannot be changed after they are created"——对象一旦创建，它表示的字符序列不能改。所以 trim()、toUpperCase() 不会把原对象擦掉重写；需要变化后的内容时，就接住方法返回的引用。

String raw = "  Blade  ";
String trimmed = raw.trim();
String upper = trimmed.toUpperCase(Locale.ROOT);

System.out.println("raw: [" + raw + "]");
System.out.println("trimmed: [" + trimmed + "]");
System.out.println("upper: [" + upper + "]");
System.out.println("raw == trimmed: " + (raw == trimmed));
System.out.println("trimmed == upper: " + (trimmed == upper));
System.out.println("trimmed == trimmed.trim(): " + (trimmed == trimmed.trim()));

raw: [  Blade  ]
trimmed: [Blade]
upper: [BLADE]
raw == trimmed: false
trimmed == upper: false
trimmed == trimmed.trim(): true

前两行没有改 raw：它仍带四个空格。trimmed 和 upper 各自指向表示新内容的对象。变量 raw 以后当然还能被重新赋值；引用变量改指向和修改 String 对象的字符是两件事。

最后一行专门拆掉一个过度推论：不可变不等于每次调用方法都创建新对象。trimmed 已经没有首尾空格，这台 Corretto 8 再执行 trim() 返回了原对象，所以 == 是 true。这个身份结果是本机实现行为，不是本篇用来判断内容的依据；要判内容仍然用 equals。

新版补充：Java 9 换了内部存储，没换掉不可变语义 JEP 254（Compact Strings，Java 9）把 String 的内部表示从 UTF-16 char 数组改为 byte 数组加编码标记：只含 Latin-1 字符时可用一字节存储，否则用 UTF-16。改变的是实现，不是字符序列不可变这条 API 约定；Java 25 的 String 文档仍保留 "values cannot be changed" 原文。以上新版内容依据 JEP 254 和 Java 25 文档，本机未运行 Java 9/25。

实测：local/examples/1-3/ImmutableString.java。API 原文见参考资料。

第 3 节

常量池：为什么有时 ==

1.2 已经确定：引用之间的 == 比的是“是不是同一个对象”。这一节只回答对象从哪里来。JLS §3.10.5 规定，内容相同的字符串字面量会驻留（intern），共享同一个 String 实例；但这条规则不能只记成“内容相同就共享”，因为 new 和运行时拼接走的是别的路径。

a, b, d, f──→对象 P："blade"字面量 / 常量表达式的驻留实例
c──→对象 C："blade"new String(...) 显式复制出的对象
e──→对象 E："blade"普通变量参与的运行时拼接结果
c.intern()──→对象 P："blade"池中已有相同内容，返回池里的引用

示意：P、C、E 是为了区分对象身份而起的名字，不是 JVM 地址；图中“池”是逻辑关系，不表示这些 String 对象住在堆以外。

表达式走哪条规则本例的身份结果
a、b相同内容的字面量共享驻留实例（§3.10.5）a == b → true
cString(String) 构造器明确初始化一个新对象a == c → false
d两个字面量拼接是常量表达式，编译期计算并当成字面量a == d → true
e普通局部变量 prefix 不是常量变量，拼接在运行时进行并创建新对象a == e → false
ffixed 是常量变量，fixed + "ade" 仍是常量表达式a == f → true

d 和 e 的内容完全相同，结果却不同，分界线是表达式是不是编译期常量。JLS §15.18.1 的原话是：字符串拼接创建的 String 对象是新对象，除非整个表达式是 §15.28 所说的常量表达式。§15.28 又允许常量表达式引用“常量变量”；§4.12.4 对常量变量的定义不是只有 final，而是基本类型或 String 的 final 变量，并且用常量表达式初始化。所以本例的 fixed 合格，普通 prefix 不合格。

intern() 是显式取规范实例的方法：池中已有 equals 相同的字符串，就返回池里那个；否则把当前字符串加入池再返回。因此 c.intern() == a 实测为 true。但不需要为了让 == 成立而给业务字符串到处 intern；第 4 节的内容判等更直接。

新版补充：字面量规则没变，Java 15 多了文本块 Java SE 25 的 §3.10.5 仍规定相同字面量共享实例、常量表达式编译期计算、运行时拼接创建不同对象；常量表达式条款移到了 §15.29，规则仍在。Java 15 通过 JEP 378 正式加入文本块（多行字符串字面量），结果仍是 String，不是新类型；Java SE 25 §3.10.6 也明确文本块表示的字符串会驻留。本机只有 JDK 8，文本块未实测。

实测：local/examples/1-3/StringIdentity.java。规范条款和构造器文档见参考资料。

第 4 节

equals：内容和 null

String.equals 的规则是：参数非 null、也是 String、并且表示相同的字符序列，才返回 true。它不看两个引用是否共享对象。因此第 1 节里 a == e 是 false，a.equals(e) 却是 true——前者问“是不是同一个”，后者问“内容是不是一样”。

但 equals 是一个实例方法，调用者本身是 null 时仍然会在 1.2 说的“顺空箭头”处倒下。把已知非空的常量放在前面，可以安全地拿它比较一个可能为 null 的输入；两边都可能为 null 时，用 Objects.equals(a, b)：

String stored = new String("WEB");
String input = null;

System.out.println("\"WEB\".equals(stored): " + "WEB".equals(stored));
System.out.println("\"WEB\".equals(input): " + "WEB".equals(input));
System.out.println("Objects.equals(stored, input): " + Objects.equals(stored, input));
System.out.println("Objects.equals(null, null): " + Objects.equals(null, null));
try {
    input.equals("WEB");
} catch (NullPointerException e) {
    System.out.println("input.equals(\"WEB\") 抛出: " + e);
}

"WEB".equals(stored): true
"WEB".equals(input): false
Objects.equals(stored, input): false
Objects.equals(null, null): true
input.equals("WEB") 抛出: java.lang.NullPointerException

Objects.equals 的规则可以背成一张小表：两个都 null → true；恰好一个 null → false；都不是 null → 调用第一个参数的 equals。它不会发明新的字符串比较规则，只是把 null 分支收好了。

真实项目里就是用来比内容

// UserServiceImpl.java 第 139–143 行
public boolean updatePassword(Long userId, String oldPassword,
        String newPassword, String newPassword1) {
    User user = getById(userId);
    if (!newPassword.equals(newPassword1)) {
        throw new ServiceException("请输入正确的确认密码!");
    }

SpringBlade 这里要判断两次输入的新密码是否是同一串字符，所以用 equals，而不是判断两个参数是否指同一对象。注意，newPassword.equals(...) 这种写法本身没有提供 null 安全；如果 newPassword 可能为 null，空值检查仍要另做。

新版补充：到 Java 25 没变化 Java 25 的 String.equals 仍以“非 null、String、相同字符序列”为 true 的条件；String 的索引和字符语义没有换成按对象身份比较。已逐句核对 Java 25 API 原文，本机未在新版运行。

实测：local/examples/1-3/EqualsNull.java。真实代码：UserServiceImpl.java 第 139–143 行。

第 5 节

拼接：+ 和 StringBuilder

第 3 节说的是拼接结果的身份，这一节看 JDK 8 的编译器怎样实现拼接。下面四个式子的输出都是 blade 或 012，但字节码并不一样：

static String runtime(String prefix) {
    return prefix + "ade";
}

static String plusLoop() {
    String s = "";
    for (int i = 0; i < 3; i++) {
        s += i;
    }
    return s;
}

static String builderLoop() {
    StringBuilder b = new StringBuilder();
    for (int i = 0; i < 3; i++) {
        b.append(i);
    }
    return b.toString();
}

compile-time: blade
runtime: blade
plusLoop: 012
builderLoop: 012

对编译后的 Concat.class 执行 javap -c -p，可以看到 Java 8 的 javac 把运行时 + 翻成 StringBuilder.append 链。单个 runtime 方法的完整核心指令是：

   0: new           #2   // class java/lang/StringBuilder
   4: invokespecial #3   // Method java/lang/StringBuilder."<init>":()V
   7: aload_0
   8: invokevirtual #4   // Method java/lang/StringBuilder.append:(Ljava/lang/String;)Ljava/lang/StringBuilder;
  11: ldc           #5   // String ade
  13: invokevirtual #4   // Method java/lang/StringBuilder.append:(Ljava/lang/String;)Ljava/lang/StringBuilder;
  16: invokevirtual #6   // Method java/lang/StringBuilder.toString:()Ljava/lang/String;
  19: areturn

指令、偏移和注释均摘自本机实测，完整原样输出见 Concat.javap.out。

所以“每次写一个 + 都手写 StringBuilder”没有从这段字节码得到支持：javac 8 已经这样翻了。真正值得看的是 new 指令在不在循环回边上：

plusLoop 每轮都会回到偏移 5，再执行偏移 10 的 new，并在偏移 25 转出一个新的 String；builderLoop 只在进入循环前执行一次 new，循环里反复 append。这是 javac 8 生成的字节码结构，不是对 JIT 优化后实际分配次数的承诺。工程写法也因此很具体：循环里持续累积内容，把 StringBuilder 放到循环外。

第 6 节

length：emoji 为什么算两个

String 的 length() 文档定义的是Unicode 代码单元（code units）的数量，不是 Unicode 代码点的数量。Java 8 的 String 以 UTF-16 表示字符串；补充字符用一对代理项表示，占两个 char 位置。😀 正是一个补充字符，所以 A😀B 有四个代码单元，却只有三个代码点。

String s = "A😀B";
int afterEmoji = s.offsetByCodePoints(0, 2);

System.out.println("s: " + s);
System.out.println("length(): " + s.length());
System.out.println("codePointCount(): " + s.codePointCount(0, s.length()));
System.out.printf("charAt(1), charAt(2): %04X %04X%n",
        (int) s.charAt(1), (int) s.charAt(2));
System.out.println("codePointAt(1): " + s.codePointAt(1));
System.out.println("offsetByCodePoints(0, 2): " + afterEmoji);
System.out.println("substring(0, afterEmoji): " + s.substring(0, afterEmoji));

s: A😀B
length(): 4
codePointCount(): 3
charAt(1), charAt(2): D83D DE00
codePointAt(1): 128512
offsetByCodePoints(0, 2): 3
substring(0, afterEmoji): A😀

索引 1 的 D83D 是高代理项，索引 2 的 DE00 是低代理项；codePointAt(1) 把这一对合成代码点 128512。substring 的起止索引仍然按代码单元算，所以想截取前两个代码点，先用 offsetByCodePoints(0, 2) 得到索引 3，再截取 [0, 3)。直接写 substring(0, 2) 会从 😀 的代理对中间切开。

换一段文本亲手看。观察器把你输入的内容拆成 UTF-16 代码单元；代理对的两格会变色。

4代码单元
3代码点
每格是这个代码单元的十六进制值。这里只显示代码单元和代码点，不做字形簇切分；更复杂的文本切分不在本篇展开。
新版补充：内部可以更省，length 的尺子没换 Java 9 的 Compact Strings 可以为 Latin-1 内容选用单字节内部存储（见第 2 节），但 Java 25 的 length() 仍明确返回 Unicode 代码单元数，String 仍提供代码点方法来处理代理对。已核对 Java 25 String API；新版内部存储未在本机实测。

实测：local/examples/1-3/Utf16.java。观察器只计算当前输入，不保存或上传内容。

第 7 节

小结和自测

带走五句话 String 对象的字符序列不可变，但引用变量可以改指向，方法调用也不保证每次返回新对象。相同字面量和字符串常量表达式共享驻留实例；new 和普通变量参与的运行时拼接会走不同对象路径。== 比对象身份，equals 比字符内容；有 null 时用已知非空常量在前或 Objects.equals。JDK 8 的循环 += 在每轮字节码里都有 new StringBuilder 指令，持续累积用循环外的 StringBuilder。length() 数 UTF-16 代码单元，emoji 等补充字符占两个位置。

五个问题

1. String x = new String("blade"); String y = new String("blade");，x == y 和 x.equals(y) 各是什么？
本例中 x == y 为 false，x.equals(y) 为 true。复制构造器初始化的是新对象；equals 只看两边是不是相同的字符序列。不要反过来记成“new 的内容不同”——两边内容完全相同。
2. final String p = "bl"; String s = p + "ade";，为什么本例 s == "blade" 是 true？把 final 去掉为什么会走另一条路？
p 是 final 的 String 变量，并且用字面量这个常量表达式初始化，所以它是常量变量；p + "ade" 整体也是常量表达式，编译期计算并驻留。去掉 final 后，p 不再是常量变量，拼接在运行时进行，规范走“新对象”路径。实测对应 StringIdentity.java 的 f 和 e。
3. s.trim() 会不会改 s 原来的对象？它是否一定创建一个新 String？
不会改原对象，这是 String 不可变的含义。但也不能推出“一定新建”：本机对已经没有首尾空格的 trimmed 再 trim()，返回了原对象。需要处理结果时接住返回值；不要靠方法是否返回新对象判断内容。
4. input 可能是 null：怎样判断它是否等于 "WEB"？如果 a、b 两个引用都可能为 null 呢？
常量和输入比较可写 "WEB".equals(input)，input 为 null 时结果是 false。两边都可能为 null 时写 Objects.equals(a, b)：都 null 得 true，一个 null 得 false，否则调用 a.equals(b)。
5. "A😀B".length() 为什么是 4？想截取前两个 Unicode 代码点，索引应该取几？
length() 数 UTF-16 代码单元：A、😀 的两个代理项、B，共 4 个。前两个代码点是 A 和 😀，结束索引是 3；可用 int end = s.offsetByCodePoints(0, 2); s.substring(0, end)，实测得到 A😀。
