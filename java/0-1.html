一个请求的一生

The life of a request

浏览器发出一个 HTTP 请求，稍后收到一段 JSON。为了算出这段 JSON，服务器那边有好几个各自独立运行的程序先后参与。这一篇拿一个真实接口的源码，按先后顺序把它们各自做的事走一遍。目的是看见全貌，不要求每一步都懂。

先猜→跟着走一趟→读那十几行代码→这门课的走法

代码引自开源项目 SpringBlade v3.7.1，可以对着源码核对。标着“示意”的数据是按规则推出来的，不是抓包结果。

第 1 节

先猜三件事

一个后台管理页面要显示“通知公告”列表。打开页面时，它发出这样一个请求：

GET /blade-desk/notice/list?current=1&size=10&title=公告
Blade-Auth: bearer eyJ0eXAiOiJKV1Qi…

随后拿到一段 JSON，里面是第一页的公告。在往下读之前，先凭直觉猜三件事。猜错没关系，这三个答案就是这一篇要讲的东西。

① 从发出到返回，这个请求一共惊动了几个独立运行的程序？
至少 5 个。网关、注册中心、公告所在的服务、数据库，还有另一个专门管“字典”的服务。它们各是各的进程，可以跑在不同的机器上。下一节一站一站看。
② 处理这个接口的那个 Java 方法，方法体有几行？
2 行。校验登录、解析参数、拼 SQL、把结果转成 JSON，这些事一行都没有出现在方法里。它们是谁做的，是第 4 节的主题。
③ 同一秒有 200 个人打开了这个页面。负责这个接口的 NoticeController 对象，内存里有几个？
1 个。程序启动时创建一个，之后所有请求都用它。200 个请求是 200 个线程在同时执行同一个对象的同一个方法。所以这个对象的字段里不能放会随请求变化的数据，否则线程之间会互相改掉对方的值。第 3 部分讲。

第 3 节

一个细节：id 为什么是字符串

上一节最后那段 JSON 里，id 是带引号的字符串，而 category 是数字。数据库里它们都是整数。这不是随手写的，实体类 Notice 里专门有一行：

@JsonSerialize(using = ToStringSerializer.class)
private Long id;

出处：blade-desk-api/…/entity/Notice.java 第 47–48 行

意思是：这个字段转 JSON 时，按字符串输出。原因在接收方。Java 的 Long 是 64 位整数，最大值是 9223372036854775807，共 19 位。JavaScript 的数字是双精度浮点数，能精确表示的最大整数是 9007199254740991，共 16 位。公告的 id 有 19 位，超出了这个范围。

在你的浏览器里试一下

下面两个按钮真的会在这个页面里执行 JSON.parse，不是写死的结果。

收到的 JSON（点上面的按钮）解析出的 id

给数字的话，最后三位变了，拿这个 id 再去请求详情就查不到这条公告。@JsonSerialize 那一行不处理任何业务，它的作用只是让数据在换形状时不走样。数值类型的范围和精度是 1.1 篇的内容。

第 5 节

  
这门课的走法

  
把上面看到的东西按“谁写的”分一下，是三层：


  

    

      
表层你每天亲手写的

      
0出发前（你在这）10回到真实项目

    

    

      
中层框架和工具替你做的

      
4工程6Spring7缓存和消息8微服务9上线和运行

    

    

      
底层框架能做到的原因

      
1对象与类型2集合与函数式3IO、网络、并发、JVM5数据库

    

  


  
数字是阅读顺序。这门课的判断是：只学表层，能照着写出一个接口，但出了问题不知道该往哪一层查。所以看完这一眼全貌之后，先沉到底层，再一层一层搭上来：

  
    
    
  • 每一部分回答一个问题，这个问题是上一部分留下的。比如学完对象，自然会问“一堆对象放在哪”，那就是集合。
    • 
    
  • 先亲手造一个小的，再用现成的大的。会写一个几十行的 HTTP 服务器、一个迷你的依赖注入容器、一个最小的 Mapper。造过一次，框架就不再是黑盒。
    • 
    
  • 不讲你已经会的。变量、分支、循环这些，0.3 用一篇带过。
    • 
    
  • 说的话要有出处。自己写的代码都实际运行过；引用别人的代码写明文件和行号；推出来的数据标“示意”；每篇末尾列参考资料，并写明每一条支撑的是文中哪句话。
    •

第 6 节

  
小结和自测

  

    带走一句话
    在这个请求里，同一份信息先后有过六种形状，至少有五个程序参与。处理它的那个方法只有两行，其余的事是网关、Spring、MyBatis-Plus 和数据库做的。这门课要讲的，就是这些“其余的事”。
  


  

    
三个问题

    

      
1. 令牌过期了。NoticeController.list 这个方法还会被执行吗？

      
      
不会。请求先到网关，网关的 AuthFilter 解析令牌失败后直接返回 401，没有把请求往后转发。blade-desk 根本不知道有过这个请求。

    

    

      
2. 假如 blade-system 这个服务挂了，公告列表会怎样？先猜，再看答案。

      
      
按源码推断，列表照常返回，只是每条公告的“类型名”是空的。IDictClient 上写了 fallback = IDictClientFallback.class：调用失败时改用这个备用实现，它返回“获取数据失败”；而 NoticeWrapper 里有一句 if (dict.isSuccess())，失败就不填名字。备用实现只有在开启了熔断组件时才生效，这个项目的共享配置里开了（doc/nacos/blade.yaml 第 27–29 行，feign.sentinel.enabled: true）。这个结论没有实际停掉服务验证过。一个服务出事时别的服务怎么不被拖垮，是 8.6 篇的内容。

    

    

      
3. 在这个项目里全文搜索，找不到 noticeService.page 里 page 方法的定义。它在哪？

      
      
在项目依赖的类库里。INoticeService 继承了 BladeTool 的 BaseService，后者又继承了 MyBatis-Plus 的 IService，page 是在那里定义的。在 IDEA 里按住 ⌘ 点方法名可以直接跳过去。
