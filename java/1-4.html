类和对象：字段跟着实例走

State, behavior, construction, and access

两次 new Counter() 得到的对象各自装着一份 value；一旦 second = first，两个变量又会改到同一个对象。类的语法从这里展开：字段保存哪个实例的状态，方法里的 this 指谁，构造器怎样把对象填好，private 与包访问到底挡住哪些写法。最后回到 SpringBlade：@Data 为什么让 private 字段仍有 public setter，手写构造器又为什么让无参 new 消失。

第 1 节

先猜：状态与构造

先读这段代码。Counter 没有声明构造器，int 字段 value 也没有写初始值；两个检查点各会得到什么？

class Counter {
    private int value;
    void increment() { value++; }
    int getValue() { return value; }
}

Counter first = new Counter();
Counter second = new Counter();
first.increment();
// 检查点 A：first.getValue(), second.getValue()

second = first;
second.increment();
// 检查点 B：first.getValue(), second.getValue()

再单独看另一个类：class NamedAccount { NamedAccount(String name) { } }。它没有无参构造器，那么 new NamedAccount() 会怎样？三道都选完，再看后面的对象图和构造顺序。

第 2 节

字段：每个实例一份

类声明定义一种类型；new Counter() 创建一个实例。没有 static 的字段叫实例字段，每个实例各有一份。所以第一次 increment 只把 first 指向对象的 value 从 0 改成 1，second 指向的另一个对象仍是 0。

first──→
Counter 实例 C1value = 1
second──→
Counter 实例 C2value = 0

检查点 A。C1、C2 是为讲解起的逻辑名称，不是 JVM 地址。

第二段的 second = first 不复制对象，只复制引用——这是 1.2 已经实测过的规则。此后 second 和 first 都指向 C1，second.increment() 改的就是 first 也能看到的那份 value：

two objects: first=1, second=0
after alias: first=2, second=2
first == second: true

还要分清字段和局部变量：对象创建时，实例字段先取得默认值（int 是 0、boolean 是 false、引用类型是 null，JLS §4.12.5），声明处的初始化器随后执行。局部变量没有这套自动赋值，读取前必须明确赋值。下一篇讲 static 时，再看另一类“跟着类走”的字段。

新版补充：实例字段这条基本规则到 Java 25 没变 Java SE 25 的 §8.3 仍区分实例字段和类字段；实例仍由 new 创建。Java 16 新增的 record 也是一种类，其实例同样用 new 创建；record 给字段、构造器和访问器增加的专门规则放到第 3、5 节。

实测：local/examples/1-4/TwoObjects.java、TwoObjects.out。对象图中的名称和箭头是逻辑示意。

第 3 节

方法：this 指谁

实例方法不是悬在空中执行的。left.rename("left") 的点号左边给出接收者，方法体里未加限定的实例字段和 this 都落在这个对象上。JLS §15.8.3 的定义很具体：在实例方法中，this 是“调用该方法所针对的对象”的引用；在构造器中，则是正在构造的对象。

class DisplayName {
    private String name = "unset";

    void rename(String name) {
        System.out.println("before: field=" + this.name
                + ", parameter=" + name);
        this.name = name;
    }

    String describe() {
        return name;
    }
}

DisplayName left = new DisplayName();
DisplayName right = new DisplayName();
left.rename("left");
right.rename("right");

rename 的参数也叫 name，它在方法体里遮蔽了同名字段。因此右边的 name 是参数，this.name 才是字段；this.name = name 把参数值写进当前对象。describe 里没有同名局部变量或参数，所以直接写 name 就能读到当前对象的字段。

before: field=unset, parameter=left
before: field=unset, parameter=right
left.describe(): left
right.describe(): right

同名方法还可以重载：在不涉及泛型的直观情况下，方法签名由名字和参数类型列表决定，返回类型不在签名里。所以参数列表不同可以共存，仅把返回类型改掉不能构成重载。构造器的重载遵循同样的思路，下一节就能看到。

新版补充：record 的访问器不叫 getX Java 16 的 JEP 395 正式加入 record。比如 record Point(int x, int y) { } 会得到名为 x()、y() 的 public 访问器，而不是 JavaBeans 风格的 getX()、getY()。方法签名和重载的基本规则仍在 Java SE 25 §8.4 中保留。record 语法依据 JEP，本机 JDK 8 未运行。

实测：local/examples/1-4/MethodsAndThis.java。this 的接收者定义见 JLS §15.8.3。

第 4 节

构造器：对象怎样填好

构造器与类同名，没有返回类型，连 void 也不写。new 表达式负责创建实例并最后返回引用；构造器负责初始化。下面这个类有字段初始化器，也有两个构造器：

class UserAccount {
    private String name = "anonymous";
    private int balance = 10;

    UserAccount() {
        this("guest", 0);
        System.out.println("no-arg body");
    }

    UserAccount(String name, int balance) {
        System.out.println("before body: name=" + this.name
                + ", balance=" + this.balance);
        this.name = name;
        this.balance = balance;
        System.out.println("two-arg body");
    }

    String describe() { return name + ":" + balance; }
}

new UserAccount("blade", 100);
new UserAccount();
1 · 分配对象实例字段先得到 0、false 或 null
→
2 · 向上构造执行父类构造过程；继承在 1.6 展开
→
3 · 当前类初始化器按源码顺序执行字段初始化器和实例初始化块
→
4 · 构造器余下主体给字段赋参数值，执行其他语句

这是 JLS §12.5 的初始化顺序。若构造器以 this(...) 委托同类的另一个构造器，先递归处理被委托者，再回来执行委托者余下的主体；当前类的字段初始化器不会沿委托链重复执行。所以无参 new 的输出依次是两参主体、无参主体：

before body: name=anonymous, balance=10
two-arg body
custom: blade:100
before body: name=anonymous, balance=10
two-arg body
no-arg body
no-arg: guest:0

before body 打印的是 anonymous 和 10，说明进入两参构造器主体时，默认值阶段已经结束，声明处的字段初始化器也已经执行。这段输出没有直接展示更早的 null 和 0；那一阶段依据 §12.5，而不是从打印结果反推。

“无参构造器”不等于“默认构造器”

UserAccount() 是我们亲手写的无参构造器。JLS 所说的默认构造器有另一个严格含义：类里一个构造器声明都没有时，编译器隐式提供一个。只要能写 new ImplicitOnly() 的 ImplicitOnly 完全没声明构造器，就符合这条规则：

class ImplicitOnly { }
new ImplicitOnly();
// 实测输出：new ImplicitOnly(): success

但只要写了一个构造器，编译器就不再补默认构造器。第 1 节的 NamedAccount 只声明了 NamedAccount(String)，所以 new NamedAccount() 实测编译失败：

错误: 无法将类 NamedAccount中的构造器 NamedAccount应用到给定类型;
  需要: String
  找到: 没有参数
  原因: 实际参数列表和形式参数列表长度不同
1 个错误

真实项目里的手写构造器

// DemoController.java 第 35–44 行
public class DemoController {

    private final DemoProperties properties;

    public DemoController(DemoProperties properties) {
        this.properties = properties;
    }
}

右边的 properties 是参数，this.properties 是当前 DemoController 的字段。这个类既然显式声明了构造器，Java 就不会再补一个无参默认构造器。项目里还有许多 @AllArgsConstructor 让 Lombok 生成构造器；谁负责调用它、依赖怎样传进来，留到 Spring 的依赖注入篇。

新版补充：Java 25 允许构造器先写 prologue Java 8 要求显式 this(...) 或 super(...) 必须是构造器主体的第一条语句。JEP 513 在 Java 25 正式加入“灵活构造器方法体”：调用前的语句段叫 prologue，可以先校验参数或初始化当前对象的字段；调用后的语句段叫 epilogue。prologue 仍不能随意读取 this 或调用当前对象的实例方法。默认构造器“仅在没有任何构造器声明时出现”的条件到 Java 25 没变。新版语法依据 JEP 513 和 Java SE 25 §8.8，本机未运行。

实测：Construction.java、DefaultConstructor.java、MissingNoArg.java。真实代码：DemoController.java 第 35–44 行。

第 5 节

封装：private 还不够

把字段写成 private，首先是限制哪些源码能直接访问它。要进一步保证“余额不会被改成负数”，还需要所有修改入口都执行同一条约束。Wallet 没有公开字段，也不提供随意赋值的 setter，只开放会检查金额的 withdraw：

class Wallet {
    private int balance;

    Wallet(int balance) { this.balance = balance; }

    boolean withdraw(int amount) {
        if (amount <= 0 || amount > balance) {
            return false;
        }
        balance -= amount;
        return true;
    }

    int getBalance() { return balance; }

    boolean sameBalance(Wallet other) {
        return this.balance == other.balance;
    }
}
withdraw(30): true, balance=70
withdraw(80): false, balance=70
withdraw(0): false, balance=70
sameBalance(new Wallet(70)): true

sameBalance 还拆掉一个常见误解：private 不是“只有这个对象自己能看”，而是“只有包围声明的类体能看”。所以 Wallet 的方法可以读取另一个 Wallet 实例的 other.balance；包里的其他类仍然不行，第 6 节会让 javac 证明这一点。

SpringBlade 的 private 字段为什么还能 set

// User.java 第 35–38、56–62 行（节选）
@Data
public class User extends TenantEntity {
    private String account;
    private String password;
    private String name;
}

User 里没有手写 getPassword 或 setPassword，但类上有 Lombok 的 @Data。@Data 的官方规则包括：给所有字段生成 getter，给所有非 final 字段生成 setter，而且生成的 getter/setter 默认是 public。于是 service 写的是方法调用，不是直接访问 private 字段：

// UserServiceImpl.java 第 58–62 行
public boolean submit(User user) {
    if (Func.isNotEmpty(user.getPassword())) {
        user.setPassword(DigestUtil.encrypt(user.getPassword()));
    }

所以“private 字段外界完全不能改”是错的；准确说法是“外界不能直接写字段，能否通过方法改，要看类提供了什么方法”。User 这种实体承担数据承载，SpringBlade 选择用 Lombok 开放访问器；Wallet 要守住余额约束，就不能再给一个不做检查的 public setBalance。两种设计服务于不同目的。

新版补充：Java 16 的 record 面向不可变数据载体 JEP 395 规定，record 的每个组件对应 private final 字段，并自动获得规范构造器、访问器、equals、hashCode 和 toString；record 本身不提供一套 JavaBeans setter。JEP 同时明确：解决可变 JavaBeans 类的需求不是 record 的目标。因此不能把 User 这类需要逐字段修改的实体机械地改成 record。以上依据 JEP 395，本机 JDK 8 未运行 record。

实测：local/examples/1-4/Encapsulation.java。真实代码：User.java、UserServiceImpl.java；生成规则见 Lombok @Data 文档。

第 6 节

包和访问控制：四道门

package org.springblade.system.user.entity; 声明当前编译单元属于哪个包；import 只是让其他包的类型可以用简单名书写。每个编译单元会自动导入 java.lang 里的 public 类型，所以 String 不用手写 import。import 不会连带导入子包。

包也参与访问控制。下面这个 Vault 特意写齐四种字段，接下来用三个包位置去访问：

package demo.model;

public class Vault {
    private int secret = 1;
    int packageValue = 2;
    protected int inheritedValue = 3;
    public int publicValue = 4;
}

前提：包含成员的类或接口本身也必须可访问。“default”在这里是访问级别的名字，不是要写到字段前的关键字。

同包的 SamePackage 能读 packageValue、inheritedValue、publicValue；跨包普通类 OtherPackage 只读到了 publicValue。对应的 javac 报错也分别验证了：同包仍读不了 private，跨包读不了包私有字段。

protected 不能简化成“子类随便访问”

跨包时，访问代码必须位于子类中；对实例字段，点号左边表达式的编译时类型还有限制。假设 ProtectedChild 在 demo.client，Vault 在 demo.model：

// ProtectedChild.java：两种写法均实测通过
int readFromThis() {
    return this.inheritedValue;
}
int readFromChild(ProtectedChild child) {
    return child.inheritedValue;
}

// ProtectedChildError.java：单独编译，确认报错
int readFromParent(Vault parent) {
    return parent.inheritedValue;
}
// 错误: inheritedValue 在 Vault 中是 protected 访问控制

原因是 JLS §6.6.2.1：在子类 S 的类体里跨包访问 protected 实例成员时，限定表达式的类型必须是 S 或 S 的子类。这里 this 和 child 都是 ProtectedChild，parent 却是 Vault。继承本身下一篇再展开，这里先记住 protected 的准确边界。

新版补充：Java 9 模块在包之外又加了一道 exports 四种成员访问级别和 protected 的上述限制在 Java SE 25 §6.6 中仍保留。JEP 261 在 Java 9 交付模块系统：在命名模块之间，一个 public 类型所在包还需要被 exports，访问方还要能读取提供方模块；public 不再单独保证处处可访问。classpath 项目和模块项目不能混为一谈。本机示例是普通 JDK 8 包访问实验，未运行模块示例。

实测：local/examples/1-4/access-src/；成功输出见 AccessValid.out，三份预期编译失败输出见对应 *Error.out。

第 7 节

小结和自测

带走六句话 每次 new 都创建实例，非 static 字段每个实例一份；引用赋值则会让多个变量指向同一实例。实例方法里的 this 指向接收者，构造器里的 this 指向正在构造的对象。字段先经历默认值和初始化器，再执行构造器余下主体；this(...) 委托不会让字段初始化器重复执行。只有完全没写构造器时才有默认构造器，手写无参构造器不叫默认构造器。private 限制直接访问，公开方法和 Lombok setter 仍能修改状态。包私有不是 public，protected 跨包实例访问还受子类和表达式类型限制。

六个问题

1. Counter a = new Counter(); Counter b = new Counter(); a.increment();，b 的 value 为什么不是 1？若接着写 b = a; b.increment();，a 又会看到什么？
两次 new 创建两个实例，各自有一份 value，所以第一次只改 a 的对象。b = a 只复制引用，此后两者指向同一个对象；再调用 b.increment()，a 也会看到同一个 value 变为 2。对应 TwoObjects 的实测。
2. 方法参数和实例字段同名时，this.name = name; 左右两边各指什么？
右边 name 是参数；左边 this.name 是当前接收者对象的实例字段。在构造器里，this 则是正在构造的对象。不能把两边都理解为字段。
3. 一个类写了 UserAccount() { this("guest", 0); }，这个无参构造器是 JLS 的默认构造器吗？字段初始化器会执行几次？
不是，它是显式声明的无参构造器。默认构造器只在类没有任何构造器声明时隐式出现。this(...) 委托链中，当前类的字段初始化器只执行一次；Construction 的两次 new 各自初始化一次，但同一次无参 new 内没有重复初始化。
4. class A { A(String x) { } } 能否写 new A()？怎样才能有一个公开的无参构造器？
不能，已有显式构造器后不会再补默认构造器。若设计需要无参入口，就按所需访问级别显式声明，例如 public A() { ... }；是否委托其他构造器由类的初始化需求决定。
5. User 的 password 是 private，UserServiceImpl 为什么还能调用 setPassword？同一个 Wallet 类里又为什么能读 other.balance？
User 上的 Lombok @Data 为非 final 字段生成 public setter，service 调的是公开方法，不是直接访问 private 字段。private 的访问边界是包围声明的类体，不是单个对象，所以 Wallet 的方法可以访问另一个 Wallet 实例的私有字段。
6. 跨包子类中，为什么 this.inheritedValue 和 child.inheritedValue 可以，parent.inheritedValue 却编译失败？
在 demo.client 的子类 ProtectedChild 中跨包访问 demo.model.Vault 的 protected 实例字段时，限定表达式类型必须是 ProtectedChild 或它的子类。this 和 child 满足，声明为 Vault 的 parent 不满足；仅“代码位于子类里”还不够。

  • JLS §7.3 Compilation Units、§7.5.1 Single-Type Import支撑：第 6 节——java.lang 隐式导入、import 让类型可用简单名表示且不导入子包

新版规则与工具文档

  • JLS（Java SE 25）第 8 章、第 6 章 §6.6支撑：第 2、3、4、6 节「新版补充」——实例字段、方法、默认构造器条件与成员访问控制在新版规范中的保留
  • JLS（Java SE 25）§7.6、§7.7、JEP 261：Module System（Java 9）支撑：第 6 节「新版补充」——命名模块中的 public 类型还受 exports 和模块可读性约束
  • JEP 395：Records（Java 16）支撑：第 2、3、5 节「新版补充」——record 是 new 创建的类；组件访问器命名、private final 字段、规范构造器和数据承载目标
  • JEP 513：Flexible Constructor Bodies（Java 25）支撑：第 4 节「新版补充」——prologue / epilogue、显式构造器调用前允许的安全语句，以及访问当前对象的限制
  • Lombok @Data 官方文档支撑：第 5 节——@Data 生成 getter、非 final 字段的 public setter，以及构造器等方法；这不是 Java 自动给普通类生成访问器
