原码、反码、补码

Sign-magnitude, Ones' Complement & Two's Complement

很多教程只给你三条计算公式：反码是"取反"，补码是"反码加一"。这一集反过来，从问题讲起：每一种表示法都是为了解决上一种的毛病才出现的。弄明白之后，byte 为什么是 −128 到 127、强转为什么会变成负数，就都能解释了。

第 1 节

原码：最直观的写法

原码就是把十进制数直接写成二进制，再规定最左边一位是符号位：0 表示正，1 表示负，剩下的位才是数值。

比如 56 写成二进制是 0111000，补齐一个字节、前面放上符号位 0，就是 00111000；−56 只把符号位换成 1：10111000。

先补两个单位。二进制里的一个 0 或一个 1 叫一个比特（bit，比特位）。一个比特能表示的东西太少，所以把 8 个比特编成一组，叫一个字节（byte），它是计算机里最小的存储单元。

那么一个字节的原码，最大能表示多少？符号位必须是 0，后面 7 位全是 1：01111111 = +127。最小呢？符号位是 1，数值位也要尽量大，全是 1：11111111 = −127。注意不是 10000000：数值部分是 0，那它读出来还是 0，只是带了个负号。

先记住一个疑问 按原码算，一个字节能表示 −127 ~ +127。可 Java 里 byte 的范围明明是 −128 ~ 127，多出来的那个 −128 是哪来的？第 5 节揭晓。
第 2 节

原码的毛病：负数越加越小

用原码算正数完全没问题。从 00000000 开始，最右一位加 1，得到 1；再加 1，进位，得到 2；然后 3、4、5……和十进制里数数一模一样。

换成负数就出事了。10000000 也表示 0（"负零"）。给它加 1，按二进制加法得到 10000001，读出来是 −1，可 0 + 1 应该等于 1。再加 1 得到 10000010，读出来是 −2，可 −1 + 1 应该是 0。越加越小。

放到数轴上就很好理解：二进制加法总是让数值位变大。数值位变大，对正数是往右走；可符号位是 1 的时候，数值位越大，这个数就越往左。我们想往正方向走一步，它实际往负方向走了一步，方向正好反了。

先从 "0（00000000）" 出发连点几次 +1，再换成从 "−0" 或 "−3" 出发对比

小结一下：原码算正数没问题，算负数时，实际走的方向和我们想要的方向相反。

第 3 节

反码：把负数那一半倒过来

既然负数那边的路是反着的，当年的设计者就想：把这一半的路也倒过来，不就顺了吗？这就是反码，它是为了解决原码不能算负数的问题出现的。规则分两种情况：

  • 正数：反码和原码一样，不变。
  • 负数：在原码的基础上，符号位不变，数值位取反（0 变 1，1 变 0）。

为什么正数不变？因为正数用原码算本来就对，没必要改；只有负数的方向反了，所以只把负数翻过来。

还是拿 −56 举例：原码 10111000，符号位不动，后面 7 位取反，得到反码 11000111。

现在用反码算 −56 + 1，正确答案应该是 −55。从最右一位加 1，连续进位三次，得到 11001000。−55 的反码是多少？55 的原码是 00110111，变负数是 10110111，再取反得 11001000，一模一样。再试 −4（11111011）：减 1 得 11111010，正是 −5；加 1 得 11111100，正是 −3。在负数范围里加减 1，反码都算对了。

第 4 节

反码的毛病：一跨过 0 就差 1

反码还没完。从 −4 开始一路加 1：−3、−2、−1，都对。−1 的反码是 11111110，再加 1 得 11111111，它是"负零"，读出来 0，也对。

可再加 1 呢？11111111 加 1，一路进位 8 次，超出一个字节的 1 丢掉，得到 00000000：还是 0！本该是 1，少了 1。

不是巧合。只要结果跨过了 0，就会差 1：

  • −5 + 2：结果没跨零，得 −3，对。
  • −5 + 6：11111010 + 00000110，丢掉溢出的 1 得 00000000 = 0，正确答案是 1，差 1。
  • −4 + 7：11111011 + 00000111 得 00000010 = 2，正确答案是 3，差 1。

上面的竖式加法里点 "−5+6" 和 "−4+7" 就能亲眼看到。原因在于反码里 0 有两种写法：00000000（+0）和 11111111（−0）。把加 1 想成往上跳一格，从负数跳到正数的路上，0 这一站要跳两次，所以跨过 0 的结果总比正确答案小 1。

动手：在反码里一步步 +1

从 −3 出发连点 +1，注意经过 0 的那两步

真实的反码机器是怎么做的 视频里把溢出的 1 直接丢掉，所以跨零时差 1。历史上真用反码的计算机（比如 1960 年代的 CDC 6600、UNIVAC 1100 系列）用的是循环进位：最高位进出来的 1 不丢，而是加回到最低位。−5 + 6 先得到 00000000，再把进位加回来，就是 00000001 = 1，结果是对的。
所以反码真正的麻烦是：两个零（判断"是不是 0"要比较两种写法），以及每次加法都可能要多加一轮进位，电路更复杂、更慢。补码把这两个问题一次解决了，所以后来几乎所有计算机都改用补码。顺带一提，反码求和今天还活着：互联网 IP 包头的校验和就是用它算的。
第 5 节

补码：错开一位，只留一个 0

问题出在 0 要跳两次。那就把多出来的那个 0 去掉：让负数整体往左挪一格。原来表示 −0 的 11111111 改成表示 −1，原来表示 −1 的 11111110 改成表示 −2……每个负数都错开一位。这就是补码。

"错开一位"换成计算规则，就是：

  • 正数：补码和原码、反码都一样。正数的原码、反码、补码三者相同。
  • 负数：补码 = 反码 + 1。这里的 +1 正是为了把多出来的那个 0 挤掉。

举两个例子：

十进制原码反码（数值位取反）补码（反码 + 1）
−1100000011111111011111111
−2100000101111110111111110
−4100001001111101111111100
−56101110001100011111001000

验证一下。−4 + 2：11111100 加两次 1 得 11111110，正是 −2。再试跨零的 −4 + 5：11111100 + 00000101，丢掉溢出的 1，得 00000001 = 1，完全正确。（在上面的竖式加法里切到"用补码算"，把 −5+6、−4+7 再算一遍。）

补码彻底解决了正负数混合计算的问题。正因为如此，计算机里数字的存储和运算，全都是用补码进行的。

动手：在补码里一步步 +1

多出来的 −128

错开一位还有个副作用：负数整体挪了一格，最左边就空出来一个位置。−127 的补码是 10000001，它左边的 10000000 没人用了。于是规定：一个字节里，10000000 表示 −128。它只有补码，没有对应的原码和反码，但这不碍事，因为计算机本来就只用补码。

这就是第 1 节那个疑问的答案：byte 的取值范围是 −128 ~ 127，多出来的 −128 是补码"省"出来的。

第 6 节

用补码解释：整数类型和类型转换

Java 的整数有四种类型：byte、short、int、long，分别占 1、2、4、8 个字节，也就是 8、16、32、64 个比特。同一个数 10，在这四种类型里的区别只是前面补了多少个 0：

隐式转换：小变大，前面补位

byte a = 10; int b = a; // 取值范围小的赋给大的，自动转换

a 在内存里是一个字节 00001010。转成 int 要变成 4 个字节，做法是在前面补位，补到 32 位，数值不变。

更正一个细节：补的不一定是 0 视频说隐式转换就是"前面补 0"，这只对正数成立。准确的规则是补符号位（叫"符号扩展"）：正数补 0，负数补 1。比如 byte −1 是 11111111，转成 int 是 32 个 1，读出来还是 −1；要是补 0，就变成 255 了。下面的演示切到"自动 byte → int"，输入一个负数试试。

强制转换：大变小，砍掉前面

int a = 300; byte b = (byte) a; // b 是多少？

300 是正数，原反补相同，作为 int 占 32 位：00000000 00000000 00000001 00101100。强转成 byte，就是把前面 3 个字节直接砍掉，只留最后 8 位 00101100。注意，砍掉的部分里有一个 1，数值就变了：剩下的 00101100 = 44。

再看 (byte) 200。200 的最后一个字节是 11001000。砍完之后，最左边的 1 成了 byte 的符号位，而计算机是按补码来读的：11001000 作为补码是 −56。所以 (byte) 200 打印出来是 −56。

验证这些数可以用 Windows 自带计算器的"程序员"模式：输入十进制看二进制，还能把字长在 QWORD / DWORD / WORD / BYTE（8 / 4 / 2 / 1 字节）之间切换，在 BYTE 下输入 11001000 就能看到 −56。

第 7 节

用补码解释：位运算

有了补码，几个直接操作比特的运算符也能看懂了。它们平时自己写得少，但读 JDK 源码时经常遇到，至少要能看懂别人在干什么。计算之前，都先把数字写成补码。

  • & 按位与：把 1 当 true、0 当 false，每一位单独算，两位都是 1 结果才是 1。200 & 10 = 8。
  • | 按位或：只要有一位是 1，结果就是 1。200 | 10 = 202。用在数字上的 & 和 | 没有短路，只能写一个符号。
  • << 左移：所有位往左挪，挤出去的不要，低位补 0。200 << 2 = 800。规律：左移一位相当于 ×2。
  • >> 右移：往右挪，挤出去的不要，高位补符号位（原来是正数补 0，负数补 1）。200 >> 2 = 50。规律：右移一位相当于 ÷2。
  • >>> 无符号右移：和右移一样，只是高位不管正负，一律补 0。

动手：位运算

橙色是移位时新补进来的位

负数右移的两个坑 ① −200 >> 2 = −50，符号保住了；−200 >>> 2 高位补 0，符号位变成 0，结果是一个很大的正数 1073741774。所以 >>> 一般只在把 int 当成"一串比特"处理时用（比如算哈希值）。
② "右移一位 = ÷2"对负奇数不完全成立：-7 >> 1 是 −4（向下取整），而 -7 / 2 是 −3（向 0 取整）。
第 8 节

本集小结

正数负数解决了什么留下的问题
原码二进制，符号位 0二进制，符号位 1最直观算负数方向相反
反码同原码符号位不变，数值位取反负数之间能算对了两个 0，跨零差 1
补码同原码反码 + 1只有一个 0，正负混算都对，还多出 −128（计算机实际使用的就是它）
一句话 计算机里的整数都以补码存储和计算：正数的原码、反码、补码都一样，负数的补码 = 反码 + 1。这样一套加法电路就能算所有正负数，0 也只有一种写法。

合上页面，试着回答

1. 为什么一个字节的取值范围是 −128 ~ 127，而不是 −127 ~ 127？
原码、反码里 0 有两种写法，所以只能表示 −127 ~ 127。补码把负数整体错开一位，去掉了 −0，空出了 10000000 这个位置，规定它表示 −128。计算机用补码存储，所以 byte 是 −128 ~ 127。
2. 写出 −5 的原码、反码、补码（一个字节）。
原码 10000101 → 反码（符号位不变、数值位取反）11111010 → 补码（反码 + 1）11111011。
3. byte b = (byte) 200; 打印出来是多少？为什么？
−56。200 作为 int 的最后一个字节是 11001000，强转砍掉前 3 个字节后，最左边的 1 变成了符号位。11001000 按补码读是 −56（取反加一得 00111000 = 56）。
4. 用反码计算 −5 + 6，为什么得到 0？
反码里 0 有 00000000 和 11111111 两种写法。结果从负数跨到正数时，0 这一站被数了两次，所以比正确答案 1 少了 1。（真实的反码机器用循环进位，把溢出的 1 加回最低位来修正。）
5. int 类型的 -8 >> 1 和 -8 >>> 1 分别是多少？
-8 >> 1 = −4，高位补符号位 1，相当于 ÷2。-8 >>> 1 = 2147483644，高位补 0，符号位变成 0，变成一个很大的正数。
