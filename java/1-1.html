数值类型和它的坑

Where the numbers bite

JS 的 Number 装下所有数；Java 把数分成好几种，int、long 装整数，double、float 装小数，各有各的边界。而跨界的时候 Java 一概不提醒：整数除法把小数部分直接砍掉，整数加过头无声地绕回负数，0.1 写进 double 的那一刻就不再是 0.1。这一篇把四类坑在 JDK 8 上逐个实测，最后落到钱上：SpringBlade 的业务代码里没有一个 double 字段，金额全部走 BigDecimal。

先猜四个输出→整数除法→溢出→传到前端→浮点→BigDecimal→自测

第 1 节

先猜四个输出

0.3 过了一遍语法，但留了四个数值问题没展开。这一篇开头先把它们摆出来：每段代码下面压着实测输出，先心算，再撕开。四个都猜对，这篇可以只看第 4 节。

四行输出全部实测自 JDK 8。下面四节逐个拆开：为什么是这个结果，规则写在规范哪里，工程里怎么躲。

第 2 节

整数除法：商往零靠

int 除以 int，结果还是 int。语言规范的说法是 "integer division rounds toward 0"：商向零取整，小数部分直接砍掉。

System.out.println(7 / 2);
System.out.println(-7 / 2);
System.out.println(-7 % 2);

3
-3
-1

-7 / 2 得 -3 不是 -4——向零取整不是向下取整。对照 JS：那里的 -7 / 2 先得 -3.5，你再 Math.trunc 一下才是 -3；Java 的整数除法一步就是这个结果。% 的余数和被除数同号，这点和 JS 的 % 一致。

两边只要有一个是浮点，就是浮点除法：

System.out.println(7.0 / 2);

3.5

0.3 的自测里撞见过一次：double average = 5 / 2; 打印 2.0——右边先按 int 算出 2，再把 2 转成 double。想要 2.5，得让除法本身在浮点里发生：5 / 2.0。

除以零要分两边说：

try {
    System.out.println(1 / 0);
} catch (ArithmeticException e) {
    System.out.println("1 / 0 抛出: " + e);
}
System.out.println(1.0 / 0.0);

1 / 0 抛出: java.lang.ArithmeticException: / by zero
Infinity

整数除以零，运行时抛 ArithmeticException（编译器不查，它不知道运行时的值）；浮点除以零不抛异常，得 Infinity。同一个 /，两种规矩，看的是操作数的类型。JS 里 1 / 0 得 Infinity——Java 只有浮点那边和它对得上。

新版补充：到 Java 25 没变化 "Integer division rounds toward 0" 这句在 Java SE 25 的规范里原文还在（§15.17.2）；整数除零抛异常、浮点除零得 Infinity 也没有变。新版本没有给除法加任何写法。（已核对 Java SE 25 规范原文，链接在参考资料。）

实测：local/examples/1-1/IntMath.java。

第 3 节

溢出：不报错，只回绕

int 装得下的上限是 2147483647（231 − 1）。加过头会怎样？规范 §4.2.2 的原话："The integer operators do not indicate overflow or underflow in any way"——不提示、不抛异常，结果绕回另一端。

int max = Integer.MAX_VALUE;
System.out.println(max);
System.out.println(max + 1);
System.out.println(max * 2);

2147483647
-2147483648
-2

亲手点一次看看。下面的读数从 2147483640 开始，二进制是此刻这 32 位的真实排布（用你浏览器的 32 位整数语义模拟）：

点 +1，盯着二进制位，过顶那一下看读数。

过顶的一瞬间没有任何动静——这正是溢出危险的原因：程序不炸，带着一个错数继续跑。

赋给 long 也救不回来

long micros = 24 * 60 * 60 * 1000 * 1000;
System.out.println(micros);
long fixed = 24L * 60 * 60 * 1000 * 1000;
System.out.println(fixed);

500654080
86400000000

一天的微秒数是 864 亿，远超 int 上限。第一行的右边全是 int 字面量，整个式子按 int 算：乘法在 int 里先溢出成 500654080，再把这个错的结果装进 long——左边声明什么类型，救不了右边已经算错的式子。任何一个字面量带上 L，整条式子就提升为 long 运算，结果才对。

有防线，但要人主动用

Java 8 的 Math 里有一组带检查的方法：addExact、subtractExact、multiplyExact、toIntExact，溢出时抛异常：

try {
    Math.addExact(max, 1);
} catch (ArithmeticException e) {
    System.out.println("addExact 抛出: " + e);
}

addExact 抛出: java.lang.ArithmeticException: integer overflow

但防线要人主动用才存在：这组方法在 SpringBlade v3.7.1 的全部业务代码里出现 0 次（grep 统计）。工程里真正的做法是选对类型——数量用 int、ID 用 long、金额用 BigDecimal（第 6 节），让值域离边界足够远，溢出够不着。

新版补充：到 Java 25 没变化 "The integer operators do not indicate overflow or underflow in any way" 在 Java SE 25 的规范里原文还在（§4.2.2，已核对）。addExact 这组方法也不是新东西，Java 8 就有。

实测：local/examples/1-1/Odometer.java。

第 4 节

传到前端的 long

SpringBlade 的实体类里，private Long id; 出现 24 次（grep 统计）。主键为什么用 long 不用 int？看它的初始化脚本里真实的主键值：

-- doc/sql/blade/blade-sword-mysql.sql 第 51 行（行太长，截断显示）
INSERT INTO `blade_client` VALUES (1123598811738675201, 'sword', …

19 位。int 的上限才 10 位数，装不下。这些主键由 MyBatis-Plus 的 IdType.ASSIGN_ID 自动生成（实体类上的标注见 Post.java 第 46 行），生成原理 8.8 篇再拆，这里只需要知道：它是 19 位的 long，后端拿着没问题。

问题出在它被发到前端的那一刻。JS 的 Number 是 64 位浮点，能精确表示的整数到 253 − 1 = 9007199254740991 为止——16 位。19 位的 ID 传过去，末位会被改掉：

后端发出：  1123598811738675201
JS 存下：  1123598811738675200   ← 末位的 1 没了

这不是假设，是你浏览器此刻的真实行为。把项目里任意一个长 ID 贴进来试：

JS Number 存下
BigInt 存下

拿这个差了一位的 ID 去查详情，查不到数据，或者查到别的记录。SpringBlade 的做法是把 Long 序列化成 JSON 字符串：

// MenuVO.java 第 44–45 行
@JsonSerialize(using = ToStringSerializer.class)
private Long id;

这个标注在全仓库出现 38 次（grep 统计）。前端收到的是 "1123598811738675201"（带引号），当字符串保管，调回后端时原样带回。别对它做 Number()，一做末位就没了。

新版补充：前端一侧的变化（BigInt，ES2020） 这一节讲的边界和 Java 版本无关：long 是 64 位、JSON 是文本格式，两条都不随 Java 版本变。变化发生在 JS 一侧：ES2020 加了 BigInt，任意精度整数，19 位 ID 原样接得住，2020 年 9 月起主流浏览器都支持（MDN）。但 JSON 语法里没有 BigInt 字面量——后端直接发 1123598811738675201n 是语法错误。所以「序列化成字符串」到今天仍是通行做法，BigInt 解决的是前端拿到字符串之后的计算问题。

源码证据见参考资料；统计命令在 local/examples/1-1/README.md。

第 5 节

浮点：误差、碰巧、NaN

System.out.println(0.1 + 0.2);

0.30000000000000004

这条你在 JS 里见过，两边都是 IEEE 754 双精度，结果一模一样。0.1 这个十进制小数在二进制浮点里没有精确表示，写进 double 的那一刻存下的已经是近似值。这句话你早知道，不展开。

float 那组"碰巧"相等

Java 比 JS 多一层：float 是 32 位单精度。开头第 3 题的答案：

System.out.println(0.1f + 0.2f == 0.3f);
System.out.println(0.1f + 0.6f == 0.7f);

true
false

第一行是 true：0.1f 和 0.2f 各自的舍入误差加在一起，恰好落回 0.3f 这个值。第二行换一组数，"恰好"就没了。结论不是"float 更准"，是浮点相等判断本来就靠不住——比较 float 或 double，别用 ==。

类型混用时还有一道窄化的坑：

System.out.println((float) 0.3 == 0.3);

false

0.3 是 double；(float) 0.3 先把它舍入成 32 位 float，和 double 比较时又被提升回 double——两次转换之后，已经不是原来那个 0.3 了。

除零不抛，NaN 不等于自己

System.out.println(1.0 / 0.0);
System.out.println(0.0 / 0.0);
double nan = 0.0 / 0.0;
System.out.println(nan == nan);
System.out.println(Double.isNaN(nan));

Infinity
NaN
false
true

第 2 节说过浮点除零不抛异常。规范 §4.2.4 补齐了另一半：浮点溢出得带符号的 Infinity，没有数学上确定结果的运算得 NaN。NaN 无序：它和任何值比较都是 false，包括它自己。所以判断一个数是不是 NaN 要用 Double.isNaN()，用 == 永远判不出来。

新版补充：浮点语义统一为 strict（Java 17） Java 17 之前，不带 strictfp 的浮点表达式允许中间结果使用更宽的指数范围，和平台相关——这个口子是为 x87 时代的硬件留的（JEP 306 的背景部分）。JEP 306 从 Java 17 起把浮点运算统一为严格语义，strictfp 修饰符成为多余。这篇里的浮点结论（0.1+0.2、除零、NaN）属于两种语义下完全一致的部分。（依据 JEP 306 原文；本机只有 JDK 8，没有在 17 上实测。）

实测：local/examples/1-1/Floats.java、FloatProbe.java（float 相等那组）。

第 6 节

BigDecimal：钱的写法

金额不能带第 5 节那种误差。SpringBlade v3.7.1 的业务代码里，private Double／private Float 字段出现 0 次；金额字段是 BigDecimal（grep 统计）：

// Order.java 第 29 行（订单实体）
private BigDecimal money;
// OrderServiceImpl.java 第 32 行（下单：金额 = 数量 × 单价 5）
BigDecimal orderMoney = new BigDecimal(count).multiply(new BigDecimal(5));

BigDecimal 是任意精度的十进制小数：值是多少、小数点后有几位，都精确保存。但它自己也有三个坑，逐个实测：

坑一：用 double 构造

System.out.println(new BigDecimal(0.1));
System.out.println(new BigDecimal("0.1"));

0.1000000000000000055511151231257827021181583404541015625
0.1

传 double 进去，BigDecimal 精确保存的是那个 double 的真实值——0.1 在 double 里本来就不是 0.1。这个例子就印在 BigDecimal 的 API 文档里，文档的原话是这个构造器的结果 "somewhat unpredictable"（有些不可预测）。规则：用字符串构造；手边只有 double 时用 BigDecimal.valueOf(0.1)，它走 Double.toString 的字符串表示（API 文档原文）。

回头看 SpringBlade 那行：new BigDecimal(count) 传的是 int，整数在 int 范围内是精确的，这行没事。但如果哪天单价从 5 改成 4.99，顺手写成 new BigDecimal(4.99) 就中招了——这是假设场景，不是仓库里存在的 bug。

坑二：equals 看标度

BigDecimal a = new BigDecimal("2.0");
BigDecimal b = new BigDecimal("2.00");
System.out.println(a.equals(b));
System.out.println(a.compareTo(b));

false
0

开头第 4 题。BigDecimal 记住的除了值还有标度（小数位数）：2.0 和 2.00 值相等、标度不同，equals 就是 false。比较金额大小用 compareTo，返回负数、0、正数，不看标度。

坑三：除不尽就抛异常

try {
    BigDecimal.ONE.divide(new BigDecimal("3"));
} catch (ArithmeticException e) {
    System.out.println("1/3 抛出: " + e);
}
System.out.println(BigDecimal.ONE.divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP));

1/3 抛出: java.lang.ArithmeticException: Non-terminating decimal expansion; no exact representable decimal result.
0.33

BigDecimal 是精确数，1/3 没有精确的小数表示，不给舍入规则它宁可抛异常。除法调用带上标度和舍入模式：这里是保留两位、四舍五入（HALF_UP）。

新版补充：到 Java 25 没变化 这三条语义到 Java 25 都没变：equals 仍看标度、除不尽且不给舍入模式仍抛异常（核对了 Java 25 的 API 文档原文，链接在参考资料）。

实测：local/examples/1-1/Money.java。

第 7 节

小结和自测

带走四句话 int ÷ int 得 int，商往零靠；int 除以零抛异常，浮点除以零得 Infinity。int 溢出不报错，绕回另一端；右边全是 int 的式子，左边赋给 long 也救不回来。19 位的 Long 主键到不了前端：JSON 里发字符串，前端别 Number()。金额用 BigDecimal：字符串构造、compareTo 比大小、除法带舍入模式。

四个问题

1. long total = 70000 * 40000; 打印 total 得到什么？
-1494967296。右边两个都是 int 字面量，按 int 算：28 亿超过 int 上限（约 21.5 亿），溢出成负数，再赋给 long。写 70000L * 40000 才得到 2800000000。两个数都在 JDK 8 上实测过。
2. 后端返回 {"id": 1123598811738675201}（JSON 数字），前端 JSON.parse 之后拿到什么？
1123598811738675200：19 位超过 Number 能精确表示的范围（253 − 1，16 位），末位被改掉。SpringBlade 的做法是序列化成字符串 "1123598811738675201"，前端当字符串保管。第 4 节的输入框里可以原样验证。
3. 两个 BigDecimal，一个 "0.10" 一个 "0.1"，要判断金额是否相等，用什么？
a.compareTo(b) == 0。equals 会把标度不同判成不相等（"0.10" 和 "0.1" 的 equals 是 false）；compareTo 只比值，不看标度。
4. 1 / 0 和 1.0 / 0.0 有什么区别？
前者是整数除法，运行时抛 ArithmeticException: / by zero；后者是浮点除法，得 Infinity，不抛异常。看操作数的类型，不看运算符。
