数值类型和它的坑

Numeric promotion, overflow, floating point and BigDecimal

单价和数量都是正数，乘出来的总额却是负数。把金额改成 BigDecimal，三条明细相加又可能和汇总计算差一分钱。这一篇就围着这笔账转：先猜结果，再点“运行”看它真正输出什么，然后顺着计算过程找出每一步的原因。读完你会知道，钱该用什么类型装、在哪一步舍入。

第 1 节

先预测：接收变量是 long，够不够？

算账之前，先给数字挑个类型。Java 的整数常用两种：int 占 32 个二进制位，long 占 64 位、能装更大的数。如果你主要来自 JavaScript，这是第一个要适应的地方——JS 只有一种 number，Java 却把整数和小数分成好几种类型，整数还分长短。

现在算一笔批量采购的账：单价 50,000 分，数量 50,000，乘积应该是 2,500,000,000 分。这组数字是特意挑的：它已经超过了 int 的上限（约 21.4 亿），却远没到 long 的上限。于是很自然地，把接收结果的变量写成 long：

先猜一下：这样写，能得到正确的总额吗？

public class PriceOverflow {
    public static void main(String[] args) {
        int unitCents = 50_000;
        int quantity = 50_000;
        long totalCents = unitCents * quantity;
        System.out.println(totalCents);
    }
}

会输出 2500000000、一个负数，还是抛出异常？想好后点运行。

-1794967296

结果是负数，而且程序正常结束了，没有任何报错。两个乘数都是 int，乘法就先按 int 算，乘积在这一步已经溢出；算完再放进 long，也只能保留这个算错的负数。变量是 long，救不了前面已经算错的乘法。下一节把转换挪个位置再试。

第 2 节

把转换放到乘法之前

接收变量已经是 long，再改它没有用。这次只移动 (long) 的位置：放在整个乘积外面，或者放在第一个乘数前面。四种写法用同一组输入，每选一种就点运行，看看哪一种让结果变回了 2500000000。

把转换放在不同位置

long assigned = unitCents * quantity;

输出

-1794967296
  1. 两个 int 先相乘，乘积超出 int 范围。
  2. 保留低 32 位，结果解释为 −1794967296。
  3. 把这个负整数转换成 long，原值已无法恢复。

选一种写法，点运行，再换一种比较。

两种带括号的写法长得很像，执行顺序却不同。(long) (unitCents * quantity) 先做完 int 乘法，转换时已经溢出；(long) unitCents * quantity 先把一个乘数变成 long，另一个也跟着变成 long，乘法这才在更大的范围里进行。

背后的规则叫二元数值提升，名字唬人，意思很简单：Java 做加、减、乘、除之前，先看两个操作数是什么类型，把它们统一到同一个类型再算，接收结果的变量不参与这个决定。统一的方向按下面四条顺序判断，命中一条就停：

  1. 有 double，就按 double 算。
  2. 否则有 float，就按 float 算。
  3. 否则有 long，就按 long 算。
  4. 否则一律按 int 算——byte、short、char 参与这类运算时，也先升成 int。

所以 int * int 得到 int，long * int 得到 long。这也解释了开篇的坑：两个 int 相乘，无论左边接什么，乘法本身都按 int 进行。要让它按 long 算，就得在乘之前把至少一个乘数变成 long。

把四种写法放在一起对照
int unitCents = 50_000;
int quantity = 50_000;
long assigned = unitCents * quantity;
long castAfter = (long) (unitCents * quantity);
long castBefore = (long) unitCents * quantity;
long checked = Math.multiplyExact((long) unitCents, (long) quantity);
System.out.println("assigned=" + assigned);
System.out.println("castAfter=" + castAfter);
System.out.println("castBefore=" + castBefore);
System.out.println("checkedLong=" + checked);
assigned=-1794967296
castAfter=-1794967296
castBefore=2500000000
checkedLong=2500000000

溢出为什么偏偏变成负数？

int 用 32 位二进制补码表示有符号整数。乘法溢出时，Java 只保留数学乘积的低 32 位，再把它当成有符号 int 来读。本例可以这样算：2,500,000,000 − 4,294,967,296 = −1,794,967,296，减去的 4,294,967,296 就是 232。换句话说，数轴在 int 的两端是接起来的：上限再加 1，就绕回了下限。

Integer.MAX_VALUE2,147,483,647
加 1 →
保留低 32 位
结果成为 int 下限−2,147,483,648

如果不想让越界悄悄发生，可以用 Math.multiplyExact、Math.addExact：结果越界时它们抛 ArithmeticException，而不是给出一个截断值。但要看清调用的是哪个重载——两个 int 实参调用的是检查 int 的版本，两个 long 实参才调用检查 long 的版本。开篇那组数在前者越界，在后者不越界。

System.out.println("maxPlusOne=" + (Integer.MAX_VALUE + 1));
try {
    Math.multiplyExact(unitCents, quantity);
} catch (ArithmeticException e) {
    System.out.println("checkedInt=" + e.getClass().getSimpleName());
}
try {
    Math.addExact(Long.MAX_VALUE, 1L);
} catch (ArithmeticException e) {
    System.out.println("checkedAdd=" + e.getClass().getSimpleName());
}
maxPlusOne=-2147483648
checkedInt=ArithmeticException
checkedAdd=ArithmeticException
顺带一个编译期就拦下的写法

long 变量也不能让一个过大的 int 字面量变合法。下面这段编译失败：字面量的类型在赋值之前就定好了，没写 L 后缀它就是 int，3,000,000,000 超出 int 范围。改成 3_000_000_000L 才是 long 字面量。

public class LongLiteral {
    public static void main(String[] args) {
        long count = 3_000_000_000;
    }
}
LongLiteral.java:3: error: integer number too large: 3000000000
        long count = 3_000_000_000;

换成 long 也不是万事大吉：long 同样有上限，只是远一些。选类型时把最大单值、数量、累计次数放在一起看，确认中间结果不会越界；想让越界当场失败、而不是悄悄绕回，就用检查运算。
第 3 节

换成 double：范围更大，就更好吗？

long 解决了这笔总额的范围问题。这时容易冒出一个念头：double 能表示比 long 大得多的数，那干脆都用 double，是不是就不怕溢出了？先别急着下结论，把一个 19 位的整数 id 转成 double 再转回来，看看它还是不是原来那个数。

long id = 9_007_199_254_740_993L;
double floatingId = id;
System.out.println("id=" + id);
System.out.println("idRoundTrip=" + (long) floatingId);
System.out.println("mixedEquality=" + (id == floatingId));
System.out.println("integerEquality=" + (id == (long) floatingId));
id=9007199254740993
idRoundTrip=9007199254740992
mixedEquality=true
integerEquality=false

转回来少了 1。9,007,199,254,740,993 是 253+1，它能装进 long，却不能被 double 精确表示——double 在这个量级已经分不清相邻的两个整数，转过去就落到了 9,007,199,254,740,992。这正是“范围”和“精度”两件事：double 范围确实大，代价是大的数不再个个精确。

那为什么 id == floatingId 还是 true？ 因为比较 long 和 double 时，又一次发生了数值提升：左边的 long 也被转成同一个近似 double，两边自然相等。这个 true 只说明“转换后的两个值相等”，不能证明“转换没丢东西”。要看有没有丢，得像 integerEquality 那样转回整数再比。需要精确的整数 ID，就让它一直待在整数或十进制文本里，别途经浮点。

到这里可以把三件事分开了：范围（装不装得下）、精度（能不能精确表示）、单位（这个数代表什么）。前两件是类型的事，第三件类型管不了：接口约定金额单位是分，1990 就是 19.90 元；另一个方法若按元理解同一个数，类型检查照样通过。示例用 unitCents、totalCents 这样的名字提醒单位，但这只是命名约定，Java 不会替这个名字强制检查单位。

类型位数范围精度
int32−2,147,483,648 ～ 2,147,483,647范围内每个整数都精确
long64上限 9,223,372,036,854,775,807范围内每个整数都精确
float32带指数，远大于 long正常值约 24 个二进制位有效精度
double64带指数，远大于 long正常值约 53 个二进制位有效精度

还有 byte（8 位）、short（16 位）、char（16 位）三种更小的整数类型，业务代码里少见，参与运算时都先升成 int；boolean 不属于数值类型。位数说的是数值格式的宽度，不是 Java 对象占用的内存。

int 和 Integer 只差首字母大小写吗？

差得不止大小写。int 是基本类型，不能是 null；Integer 是包装类，可以引用一个整数对象，也可以是 null。参与加法时 Integer 会自动“拆箱”取出 int 值，而对 null 做这一步会抛异常——不能把“没传”自动当成 0。

Integer count = null;
try {
    int next = count + 1;
    System.out.println(next);
} catch (NullPointerException e) {
    System.out.println("nullUnboxing=" + e.getClass().getSimpleName());
}
nullUnboxing=NullPointerException

Long/long、Double/double 也有同样的区别。接口里缺一个值时，该拒绝、补默认值还是保留为空，要由字段含义决定——不能把“没传”自动当成 0。

第 4 节

除法：5 / 2 等于几？

转换放在哪一步，不只影响乘法。5 除以 2，先除再转 double，和先转 double 再除，会得到同一个数吗？先猜，再运行，留意中间两行。

System.out.println("intDivision=" + (5 / 2));
System.out.println("castQuotient=" + (double) (5 / 2));
System.out.println("castOperand=" + ((double) 5 / 2));
System.out.println("negativeDivision=" + (-5 / 2));
System.out.println("negativeRemainder=" + (-5 % 2));
intDivision=2
castQuotient=2.0
castOperand=2.5
negativeDivision=-2
negativeRemainder=-1

5 / 2 两边都是 int，按 int 除，小数部分直接丢掉，得 2。(double) (5 / 2) 先得到整数 2 再转成 2.0，丢掉的小数找不回来；(double) 5 / 2 先把 5 转成 double，除法按 double 执行，才得到 2.5。和乘法一样：只在最终结果上补转换，补不回此前丢掉的信息。

负数还暴露另一种误判：整数除法是向零截断，不是数学上的向下取整。所以 −5 / 2 是 −2（朝零的方向砍掉小数），而不是 −3；对应余数 −1，满足 −5 = (−2) × 2 + (−1)。

往小转：强转不检查，toIntExact 检查

把 long 转回 int 是窄化，会丢弃高位，超范围也不报错；想在超范围时拒绝，用 Math.toIntExact。

long large = 2_500_000_000L;
System.out.println("narrowed=" + (int) large);
try {
    Math.toIntExact(large);
} catch (ArithmeticException e) {
    System.out.println("checkedNarrow=" + e.getClass().getSimpleName());
}
narrowed=-1794967296
checkedNarrow=ArithmeticException
前四节可以收拢成两句话：运算按什么类型进行，由操作数决定，接收变量救不了已经算错的结果；范围和精度是两件事，double 范围大，代价是大数不再个个精确。接下来换到小数，这两句话还会以新的形式出现。
第 5 节

0.1 存进去时，就已经不是 0.1

大整数可能表示不准，小数也一样。你大概在 JavaScript 里见过 0.1 + 0.2 !== 0.3——Java 的 double 和 JS 的 number 是同一种二进制浮点格式，所以这里一模一样。这次多看一行：单独打印 0.1 看起来很正常，那它到底存的是什么？下面用 JDK 的 BigDecimal 把 double 的实际值完整展开（使用时导入 java.math.BigDecimal）。

System.out.println("doubleSum=" + (0.1 + 0.2));
System.out.println("doubleEquality=" + (0.1 + 0.2 == 0.3));
System.out.println("printedTenth=" + 0.1);
System.out.println("exactDoubleTenth=" + new BigDecimal(0.1).toPlainString());
doubleSum=0.30000000000000004
doubleEquality=false
printedTenth=0.1
exactDoubleTenth=0.1000000000000000055511151231257827021181583404541015625

问题出在加法之前。十进制小数的每一位对应 1/10、1/100、1/1000；二进制小数的每一位对应 1/2、1/4、1/8……。有限个二进制小数位加起来，化成分数后分母只能是 2 的幂。

1/20.5
1/40.25
1/80.125
1/160.0625

所以 0.5 能精确表示，0.1 不能：0.1 = 1/10，最简分母里还有因子 5，写不成有限个二进制位，它的二进制展开是 0.0001100110011… 无限循环。double 精度有限，读到字面量 0.1 时就已经用一个邻近值替代了它——上面那串长长的十进制就是这个邻近值的精确样子。加法再按浮点规则舍入，最终打印 0.30000000000000004。

那为什么单独打印 0.1 又看不出问题？ 默认输出用的是 double 的十进制字符串表示，只给出足以区分相邻值的位数，不会把精确值的所有小数位都列出来。打印成“0.1”和实际存着精确的十分之一，是两件事。

double 适合允许近似的测量和计算；需要按十进制规则精确计算的价格，本篇用 BigDecimal。把所有 == 换成“差值小于 0.000001”也不是通用修复：容差要和量纲、量级、误差要求一起定义，代替不了金额的舍入规则。
除以零：整数和浮点的失败方式也不同 
try {
    int zero = 0;
    System.out.println(1 / zero);
} catch (ArithmeticException e) {
    System.out.println("integerZero=" + e.getClass().getSimpleName());
}
System.out.println("floatingZero=" + (1.0 / 0.0));
System.out.println("zeroOverZero=" + (0.0 / 0.0));
double nan = Double.NaN;
System.out.println("nanEqualsSelf=" + (nan == nan));
System.out.println("isFinite=" + Double.isFinite(1.0 / 0.0));
integerZero=ArithmeticException
floatingZero=Infinity
zeroOverZero=NaN
nanEqualsSelf=false
isFinite=false

整数除以零抛异常；浮点 1.0 / 0.0 得到正无穷，0.0 / 0.0 得到 NaN（非数值），NaN 连和自身比较都不相等。若要求一个有限的 double，可用 Java 8 的 Double.isFinite 检查——“没抛异常”不等于计算有效。

第 6 节

BigDecimal：从文本进来，别经过 double

既然 double 存 0.1 本身就偏了，那换成 BigDecimal 总该精确了吧？先看输入这一步。下面五个式子都在处理“0.1”或“0.1 + 0.2”，有的传字符串，有的传 double，有的先算加法再转换。先猜哪些能保持 0.1 或 0.3，再运行对照。

BigDecimal fromText = new BigDecimal("0.1");
BigDecimal fromDouble = new BigDecimal(0.1);
BigDecimal fromValueOf = BigDecimal.valueOf(0.1);
BigDecimal fromSum = BigDecimal.valueOf(0.1 + 0.2);
System.out.println("text=" + fromText.toPlainString());
System.out.println("double=" + fromDouble.toPlainString());
System.out.println("valueOf=" + fromValueOf.toPlainString());
System.out.println("valueOfSum=" + fromSum.toPlainString());
System.out.println("decimalSum=" + fromText.add(new BigDecimal("0.2")).toPlainString());
text=0.1
double=0.1000000000000000055511151231257827021181583404541015625
valueOf=0.1
valueOfSum=0.30000000000000004
decimalSum=0.3

new BigDecimal("0.1") 从十进制文本准确构造出十分之一；new BigDecimal(0.1) 则准确接收了那个 double 的实际近似值——它没有再算错，只是忠实保留了一个已经偏离的输入。BigDecimal.valueOf(0.1) 走的是 double 的规范字符串表示，所以这次得到 0.1；但 valueOf(0.1 + 0.2) 仍是 0.30000000000000004，因为它无法推断运算前的十进制意图。结论：想做十进制计算，就从十进制输入开始，并一路保持它，别让中途经过 double。

2.0 和 2.00，为什么 equals 说不相等？

算对了金额，比较时还可能遇到意外。下面比较 2.0 和 2.00，先看 equals 和 compareTo 两行，另外两行稍后解释原因。

BigDecimal a = new BigDecimal("2.0");
BigDecimal b = new BigDecimal("2.00");
System.out.println("unscaled=" + a.unscaledValue() + "," + b.unscaledValue());
System.out.println("scale=" + a.scale() + "," + b.scale());
System.out.println("equals=" + a.equals(b));
System.out.println("compareTo=" + a.compareTo(b));
unscaled=20,200
scale=1,2
equals=false
compareTo=0

关键在于 BigDecimal 怎么存一个数：它用一个整数（unscaledValue）配上一个小数位数（scale）来表示，关系是 unscaledValue × 10−scale。2.0 存成 20 × 10−1，2.00 存成 200 × 10−2，数值相同，但记录它的整数和 scale 不同：

2.0

20 × 10−1

unscaledValue = 20 · scale = 1
2.00

200 × 10−2

unscaledValue = 200 · scale = 2

equals 同时检查数值和 scale，所以这里返回 false；compareTo 只按数值比，返回 0 表示相等。判断金额大小，按意图写 a.compareTo(b) > 0、== 0 或 < 0（这里和 0 比的是方法返回的 int）。需要“两位小数”时用 setScale(2, 舍入模式) 调整 scale。

加了 0.50，原来的金额变了吗？

下面两次都调用 add，第二次多了一个赋值。先想：两个 println 会不会都打印 10.50？

BigDecimal amount = new BigDecimal("10.00");
amount.add(new BigDecimal("0.50"));
System.out.println("ignoredResult=" + amount.toPlainString());
amount = amount.add(new BigDecimal("0.50"));
System.out.println("assignedResult=" + amount.toPlainString());
ignoredResult=10.00
assignedResult=10.50

BigDecimal 不可变：add 不会改动原对象，而是返回一个新对象，必须接住返回值才有用。subtract、multiply、divide，以及名字像 setter 的 setScale，全都如此。这里第二次把返回值重新赋给 amount，变量才指向计算后的数。

BigDecimal 能精确做这里的有限十进制加法和乘法，不代表任意运算都能精确结束。1 ÷ 3 的十进制也无限循环：要么拒绝，要么明确约定舍入。这就引出下一节。
第 7 节

保留两位小数，还要说清在哪一步

先算 1 ÷ 3：第一种写法要求精确结果，第二种允许按指定规则舍入。运行后看程序分别怎样结束。

try {
    BigDecimal.ONE.divide(new BigDecimal("3"));
} catch (ArithmeticException e) {
    System.out.println("exactThird=" + e.getClass().getSimpleName());
}
System.out.println("roundedThird=" + BigDecimal.ONE
        .divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP).toPlainString());
exactThird=ArithmeticException
roundedThird=0.33

不带舍入的 divide 要求精确商，1/3 写不成有限十进制，于是抛异常；带上 2, RoundingMode.HALF_UP 才明确要求保留两位、按 HALF_UP 舍入，得到 0.33。RoundingMode 来自 java.math.RoundingMode。

“保留两位”还没说完规则

HALF_UP 就是常说的四舍五入：取最近的值，正好居中时远离零。但“居中时怎么办”还有别的选择，负数尤其能看出差别。把 1.245 和 −1.245 保留两位：

模式规则1.245−1.245
HALF_UP取最近值，居中时远离零1.25-1.25
HALF_EVEN取最近值，居中时保留末位偶数1.24-1.24
DOWN向零截断1.24-1.24
FLOOR向负无穷1.24-1.25

这里只列与本篇相关的四种。另有 CEILING（向正无穷）和 UNNECESSARY（要求无须舍入，否则抛异常），后者下一节的报价程序会用到。注意 HALF_UP 不能笼统理解成“遇 5 就往数轴右边进一位”：负数居中时是向更负的一侧舍入。

逐条舍入，与最后舍入，不一定相等

再做一笔小额计算：三条明细，每条原价 0.05 元，乘以系数 0.10，得到每条 0.0050 元。两种算法都保留两位、都用 HALF_UP，只改变舍入的时机。总额会一样吗？

先舍入每条，还是先求和？

BigDecimal exactLine = new BigDecimal("0.05").multiply(new BigDecimal("0.10"));
BigDecimal roundedLine = exactLine.setScale(2, RoundingMode.HALF_UP);
BigDecimal roundEach = roundedLine.multiply(new BigDecimal("3"));
0.0050 → 0.01；三条合计：0.01 × 3
0.03 元

每条先舍入成 0.01 元，三条相加得到 0.03 元。

两边都按各自规则算对了。 差的一分钱来自舍入顺序，不是 BigDecimal 算术失效。要求明细相加等于单据金额时，得先约定明细是否已舍入、单据如何汇总；不能只写一句“统一使用 BigDecimal”就当规则完整。

把两种算法放在一起

第 8 节

写一个报价程序

现在把这些规则放回一个完整程序：接收单价、数量和折扣系数，算出原价与应付金额。为这个例子约定三件事：

  • 单价以元输入，非负，必须能精确到分；多出的非零小数位直接拒绝。
  • 数量必须是 int 范围内的正整数；折扣系数在 0 到 1 之间，例如 0.85 表示收取原价的 85%。
  • 先算单价 × 数量，再乘折扣系数，只在最终应付金额处保留两位，采用 HALF_UP。

单价和折扣系数以十进制文本进入 BigDecimal，计算途中也保持十进制。main 的 args 依次接收这三个字符串。先找到代码里的两次 setScale：第一次检查输入能否精确到分，第二次才是在计算结束时舍入。代码下方可以切换参数，看正常计算和拒绝输入各走到哪里。

import java.math.BigDecimal;
import java.math.RoundingMode;

public class PriceQuote {
    public static void main(String[] args) {
        if (args.length != 3) {
            System.err.println("用法：PriceQuote 单价 数量 折扣系数");
            System.exit(2);
        }
        try {
            BigDecimal unitPrice = new BigDecimal(args[0]);
            int quantity = Integer.parseInt(args[1]);
            BigDecimal rate = new BigDecimal(args[2]);
            if (unitPrice.signum() < 0 || quantity <= 0
                    || rate.compareTo(BigDecimal.ZERO) < 0
                    || rate.compareTo(BigDecimal.ONE) > 0) {
                throw new IllegalArgumentException("单价须非负，数量须为正整数，折扣系数须在 0 到 1 之间");
            }
            unitPrice = unitPrice.setScale(2, RoundingMode.UNNECESSARY);
            BigDecimal subtotal = unitPrice.multiply(BigDecimal.valueOf(quantity));
            BigDecimal payable = subtotal.multiply(rate).setScale(2, RoundingMode.HALF_UP);
            System.out.println("原价=" + subtotal.toPlainString());
            System.out.println("应付=" + payable.toPlainString());
        } catch (NumberFormatException e) {
            System.err.println("输入错误：单价和折扣系数须为十进制数，数量须为 int 范围内的整数");
            System.exit(2);
        } catch (ArithmeticException e) {
            System.err.println("输入错误：单价必须能精确到分");
            System.exit(2);
        } catch (IllegalArgumentException e) {
            System.err.println("输入错误：" + e.getMessage());
            System.exit(2);
        }
    }
}

程序只用 JDK 内置的类：parseInt 解析整数，signum() 返回负、零、正对应的 −1、0、1，compareTo 检查折扣范围。输入错误时输出到标准错误并以退出码 2 结束；三个 catch 分别处理格式、单价精度、数值范围三类问题。

输出

原价=59.70
应付=50.75

19.90 × 3 = 59.70，再乘 0.85 得到 50.7450，最后舍入为 50.75。

试着比较 19.900 和 19.901：多一位小数，都会被拒绝吗？

toPlainString() 把结果写成普通十进制，避免科学计数法。至于单价里多余的小数位，UNNECESSARY 检查的是“去掉它是否改变数值”：19.900 能精确变成 19.90，19.901 不行。如果还要求输入文本最多两位小数，那要另外检查格式。

这个例子把注意力放在金额表示和舍入上。接入实际业务时，还要补上金额与数量的上限，并明确币种、税费和尾差如何处理。

四个问题

1. Math.multiplyExact(unitCents, quantity) 的返回值交给 long，会避开本例的异常吗？
不会。两个实参都是 int，调用 int 版本，计算先因超过 int 上限而抛 ArithmeticException。把至少一个实参改为 long，才能选择 long 版本；检查范围取决于方法参数及重载，接收变量来不及改变它。
2. id == floatingId 是 true，可以证明 long 转 double 没有丢数据吗？
不能。比较时 long 也提升为 double，可能两边都变成同一近似值。本篇的 idRoundTrip 已显示返回 long 后少了 1，而 mixedEquality 仍是 true。
3. new BigDecimal("2.0").equals(new BigDecimal("2.00")) 为什么不适合直接回答“金额一样吗”？
它还比较 scale，因此返回 false。如果问题只要求比较数值，compareTo 返回 0 才表示数值相等。若业务还关心表示精度，是否保留 scale 就是另一个问题。
4. 将 PriceQuote 的参数换成 0.05 3 0.10，应付是多少？能改成“每件先舍入”而不影响结果吗？
按该程序约定应付 0.02。若改成每件先算 0.005 并舍入到 0.01，再乘 3，结果是 0.03。两种算法的区别就在于舍入发生的位置；改之前要先确定想实现哪种业务口径。
