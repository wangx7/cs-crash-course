Java 是怎么跑起来的

From .java to a running JVM

0.1 里的 blade-desk 服务，在服务器上是由它 Dockerfile 最后一行的 java -jar app.jar 启动的。从一个 .java 源文件到这条命令，中间要经过编译、加载、打包。这一篇在命令行里把这几步亲手做一遍，打开编译出来的文件看里面存了什么，再故意弄坏几次，看错误出在哪一步。最后把每条命令对应到 IDEA 的菜单和设置。

编译和运行→打开 .class→故意弄坏→版本号→打包→IDEA

第 1 节

两条命令：javac 和 java

JDK 里有两个命令是这一篇的主角：javac 是编译器，java 是启动 JVM（Java 虚拟机）的命令。下面的终端从一个只打印一行字的文件开始。每点一次“下一条命令”执行一条；有些命令执行前会先让你猜结果。

这一段里有两件事后面一直要用：

  • javac 的产物不是 macOS 能直接执行的程序，而是 .class 文件，里面是给 JVM 看的指令，叫字节码。同一个 .class 拷到 Linux 服务器上，由那里的 JVM 执行。
  • javac 收的是文件名，java 收的是类名。JVM 拿到类名以后，自己去找对应的 .class 文件。“去哪找、什么时候找”是第 3 节的内容。
第 2 节

打开 Hello.class

刚才生成的 Hello.class 一共 416 个字节，下面是它的全部内容（十六进制）。这个浏览器不是写死的说明图：页面里的脚本按 Java 虚拟机规范第 4 章的格式，把这 416 个字节一项一项解析出来，列在右边。点右边的某一项，左边对应的字节会亮起来；点左边的任意一个字节，也会跳到它所属的那一项。

先别急着看说明，带着下面四个任务去找。第四个任务请先猜一下能不能找到。

  • 找到“你好，JVM”这几个字存在哪
  • 找到 main 方法编译成的指令（只有 9 个字节）
  • 找到一个你没有写过的方法
  • 找到 println 的代码。先猜：它在这个文件里吗？
点右边列表里的一项，或者点左边任意一个字节。

四个任务做完会发现：

  • 源码里只有一个方法，文件里有两个。多出来的 <init> 是构造器：类里一个构造器都没写时，编译器按语言规范补一个默认的，它只调用父类 Object 的构造器。
  • println 的代码不在这里。文件里只有一串名字：类 java/io/PrintStream、方法名 println、描述符 (Ljava/lang/String;)V（收一个 String，返回 void）。连 System、Object 也一样，都只是名字。

class 文件之间是靠名字互相引用的，不是靠地址。名字什么时候换成真正的类和方法、换不成会怎样，是下面三节的内容。

第 3 节

用到时才去找

换一个有两个类的例子。App 只在命令行带了参数时才会用到 Report：

前端打包时，一个 import 指向的文件不存在，构建就会失败。Java 不一样：编译时检查过，运行时 JVM 还要按名字再找一次，而且是在某条指令第一次真正用到那个类时才去找。没走到那一行，缺了也不知道。这个实验在 JDK 25 上重做一遍，结果相同。

Java 虚拟机规范对此留了余地：可以用到时再找，也可以在一开始全部找好，只要求错误在“用到”的那一刻抛出。所以准确的说法是“实测的这两个 JVM 是用到时才找”，不是“Java 规定用到时才找”。

在这个例子里，NoClassDefFoundError 说的是：编译时这个类在，运行时找不到了。注意它和 ClassNotFoundException 的关系：后者是“找的那一步”失败，JVM 把它包成前者抛给你，调用栈里的 Caused by 就是它。

第 4 节

只重新编译一个文件

上一节是整个类不见了。更常见的情况是类还在，但内容变了。下面的 Main 用到了 Shop 的三样东西：一个方法、一个常量、一个带参数的方法。我们会改三次 Shop.java，每次只重新编译 Shop，Main.class 一直不动。

三次改动，三种结果，原因是同一个：

  • 方法按名字和描述符找。Main.class 里记的是“Shop 类里叫 greet、描述符 ()Ljava/lang/String; 的方法”。方法体换了，名字和描述符没变，就找得到新的；参数变了，描述符就变了，旧的那个找不到，报 NoSuchMethodError。
  • 常量例外。static final 且用常量初始化的字段，语言规范要求编译器把值直接写进用它的类，不留引用。所以改了它，用到它的类必须重新编译。
  • 编译器只能检查编译那一刻它看得见的东西。两边一起编译时，参数不对立刻报错；分开编译，错误就推迟到运行时。

这和后端项目的关系：在 Maven 工程里，你的代码是对着某个版本的 jar 编译的，运行时 classpath 上放的却可能是另一个版本。依赖树里同一个库出现了几个版本时，Maven 只留下一个（规则见参考资料里的 Maven 文档）。留下的那个如果少了你调用的方法，表现就和上面第三次改动一模一样：启动正常，执行到那一行才报 NoSuchMethodError。依赖管理在 4.1 篇讲。

第 5 节

52 和 69：class 文件的版本号

第 2 节的字节浏览器里，魔数后面紧跟着版本号 00 34，也就是 52。每个 JDK 版本的编译器默认产出自己那一版的格式，JVM 只认得不比自己新的格式：

Java 8 → 52Java 11 → 55Java 17 → 61Java 21 → 65Java 25 → 69

规律是 44 加上版本号。52 和 69 是下面实测出来的，其余三个按 Java 虚拟机规范 Java SE 25 版第 4.1 节的表。

这件事和你直接相关。这台 Mac 上装的 JDK 只有 25；SpringBlade 的服务在容器里跑的是 Java 8：

FROM anapsix/alpine-java:8_server-jre_unlimited
…
ADD ./target/blade-desk.jar ./app.jar
…
ENTRYPOINT ["java", "-Djava.security.egd=file:/dev/./urandom", "-jar", "app.jar"]

出处：blade-service/blade-desk/Dockerfile 第 1、11、13 行。镜像名里的 8_server-jre 表示 Java 8 的运行环境（JRE，只有 java，没有 javac）。

下面这个小程序用了 String.isBlank()，这是 Java 11 才加的方法。终端里的命令会在两个 JDK 之间切换，每行开头的标签写着用的是哪一个。

三种编译方式，结论分别是：

用 JDK 25 编译时class 版本在 JDK 8 上
javac Check.java69加载时报 UnsupportedClassVersionError，一行都不执行
javac -source 8 -target 852能加载，执行到 isBlank 才报 NoSuchMethodError；在你的 Mac 上测试则一切正常
javac --release 8—编译时就报错：Java 8 的 String 没有这个方法

第二种最危险，因为它在本机测不出来。而 SpringBlade 的 pom.xml 第 136–137 行写的正是 <source> 和 <target>（值为 1.8），没有用 release。也就是说，用 JDK 25 来构建这样的工程，就落在第二种情况里。最省事的做法是让构建用的 JDK 本身就是 8，第 7 节说在 IDEA 里改哪里。你们 BladeX 的 pom.xml 怎么写的，要打开自己的文件看。

第 6 节

打成 jar

一个服务有几百个 class 文件，再加上几十个依赖库，不可能一个个拷到服务器上。jar 就是把它们装进一个 zip 格式的文件。拿第 4 节的两个类试一下（命令和输出都来自 JDK 8）：

$ jar cfe shop.jar Main Main.class Shop.class
$ jar tf shop.jar
META-INF/
META-INF/MANIFEST.MF
Main.class
Shop.class
$ unzip -p shop.jar META-INF/MANIFEST.MF
Manifest-Version: 1.0
Created-By: 1.8.0_512 (Amazon.com Inc.)
Main-Class: Main
$ java -jar shop.jar
欢迎光临
每页 10 条
¥199

jar cfe 里的 e 指定入口类，它被写进 MANIFEST.MF 的 Main-Class。java -jar 读这一行，知道该从哪个类的 main 开始，并且把这个 jar 当作找类的地方（classpath）。

Spring Boot 打出来的 blade-desk.jar 多了一层。JDK 没有提供加载“jar 里套着的 jar”的标准办法，而一个服务的几十个依赖都是 jar。Spring Boot 的做法是把它们原样放进去，再放一个自己的启动器负责读取：

blade-desk.jar
├─ META-INF/MANIFEST.MF
│     Main-Class:  org.springframework.boot.loader.JarLauncher   ← java -jar 先启动它
│     Start-Class: 带 main 方法的启动类                           ← 它再去调用这个
├─ org/springframework/boot/loader/…   启动器自己的 class
├─ BOOT-INF/classes/                   项目代码编译出的 class
└─ BOOT-INF/lib/                       依赖的 jar，每个都原样放着

结构依据 Spring Boot 2.7.18 文档的“可执行 jar 格式”一章，没有实际构建 SpringBlade 解开核对。blade-desk 的启动类是 org.springblade.desk.DeskApplication。

所以第 4 节说的“运行时 classpath 上是哪个版本的 jar”，在 Spring Boot 服务里就是 BOOT-INF/lib/ 里放的那一个。

打开公司项目以后，先看第一行和最后一行这两处。要是显示的是 25，你就处在第 5 节表格的第二行：本机一切正常，部署到 Java 8 的服务器上，用到新方法的那一行才会出错。

第 8 节

小结和自测

带走一句话 javac 把源码编译成按名字互相引用的 class 文件；java 启动 JVM，由它在 classpath 上按名字找这些文件，用到时才找。编译时检查过的东西，运行时还要再对一次，对不上就是 NoClassDefFoundError、NoSuchMethodError、UnsupportedClassVersionError。常量是例外，它在编译时就被抄进了用它的类。

三个问题

1. 新服务上线，日志里只有一行错误：UnsupportedClassVersionError: … (class file version 61.0), this version of the Java Runtime only recognizes class file versions up to 52.0。发生了什么？该改哪里？
61 = 44 + 17，说明这个 class 是用 JDK 17 默认设置编译的；52 说明服务器上跑的是 Java 8。改构建这一侧：用 JDK 8 构建，或者用 JDK 9 以上构建并加 --release 8。只加 -source 8 -target 8 能让这条错误消失，但可能换成第 5 节里的 NoSuchMethodError。
2. SpringBlade 的 pom.xml 第 140 行给编译器加了一个参数 -parameters。它改变了 class 文件里的什么？谁需要它？
默认情况下，javac 不把方法的参数名写进 class 文件（实测：对 list(String title, int size) 用 javap -v 查看，找不到 title 和 size）。加上 -parameters 后，class 文件里多了一个 MethodParameters 属性，记着这两个名字。Spring 需要它：参数名和请求参数同名时，@PathVariable、@RequestParam 可以不写名字，Spring 就是从这里读到参数名的（Spring 文档的原话是需要调试信息或者 -parameters）。“框架怎么读到 class 文件里的信息”是 3.10 篇的内容。
3. 你的代码编译时依赖某个库的 2.0 版，调用了 2.0 才有的方法 X。运行时 classpath 上实际是 1.0 版。程序会在什么时候出错、报什么？
启动不报错（第 3 节：用到时才找）。执行到调用 X 的那一行时报 NoSuchMethodError，没用到 X 的功能照常工作。如果你用的是 2.0 新增的一整个类，报的就是 NoClassDefFoundError。所以这类错误可能在上线以后、有人第一次用到某个功能时才出现。

参考资料

每一条后面写了它支撑的是哪句话。链接和原文在 2026-11-12 逐条打开核对过。

规范

  • Java 虚拟机规范（Java SE 8）§4.1 The ClassFile Structure支撑：第 2 节字节浏览器的解析格式；魔数是 0xCAFEBABE；JDK 1.k 支持到 44+k 版，即 Java 8 是 52
  • Java 虚拟机规范（Java SE 25）§4.1支撑：第 5 节的版本号表；Java SE 25 支持的 major_version 是 45 到 69
  • Java 虚拟机规范（Java SE 8）§5.4 Linking支撑：第 3 节：规范允许“用到时再解析”（lazy）和“一次全部解析”两种实现
  • Java 虚拟机规范（Java SE 8）§5.3 Creation and Loading支撑：第 3 节：加载器抛出 ClassNotFoundException 时，JVM 必须抛出以它为原因的 NoClassDefFoundError
  • Java 虚拟机规范（Java SE 8）§5.4.3.3 Method Resolution支撑：第 4 节：按名字和描述符找方法，找不到时抛出 NoSuchMethodError
  • Java 语言规范（Java SE 8）§13.1 The Form of a Binary支撑：第 4 节：对 static 常量的引用必须在编译时换成值，class 文件里不应留下对该字段的引用
  • Java 语言规范（Java SE 8）§13.4.9 final Fields and static Constant Variables支撑：第 4 节：改了常量的值，已编译的类不重新编译就看不到新值
  • Java 语言规范（Java SE 8）§15.28 Constant Expressions支撑：第 4 节："每页 " + Shop.PAGE_SIZE + " 条" 是常量表达式，所以 javac 能把它算成一个字符串
  • Java 语言规范（Java SE 8）§8.8.9 Default Constructor支撑：第 2 节：类里没写构造器时，编译器补一个默认构造器

  • JDK 8 工具文档：java支撑：第 1 节：java 的参数是类名；第 6 节：-jar 时入口类由 MANIFEST 的 Main-Class 指定
  • JDK 8 工具文档：javac，Searching for Types 一节支撑：第 3 节：javac 找到被引用类型的源文件时，默认也编译它
  • JEP 330：Launch Single-File Source-Code Programs支撑：第 1 节：JDK 11 起 java 命令可以直接运行单个源文件
