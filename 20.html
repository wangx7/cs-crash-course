Files & File Systems

第 0 节

文件格式与文本文件

上一集我们讲了数据存储：磁带、硬盘这样的技术，能在不通电的情况下长期存储上万亿个位。这非常适合记录一大块相关的数据，也就是我们常说的计算机文件。你肯定见过很多种文件，比如文本文件、音乐文件、照片和视频。今天我们来讲文件是怎么工作的，以及计算机怎样用文件系统把它们管理得井井有条。

文件里装任意的、没有格式的数据完全合法，但如果文件里的数据以某种方式组织起来，才最有用、最实际。这种组织方式叫文件格式（file format）。你可以发明自己的格式，程序员也时不时这么做，但通常用现成的标准最好、最省事，比如 JPEG 和 MP3。

来看几种简单的文件格式。最直接的是文本文件，也叫 TXT 文件，里面装的是……惊喜吧！文字。和所有计算机文件一样，它只是一长串以二进制存储的数字。如果看文本文件在存储器里的原始值，是这个样子的。我们可以把它看成十进制数，但这仍然帮不了我们读出文字。解读这些数据的关键，是知道 TXT 文件用的是 ASCII——第 4 集讲过的一种字符编码标准。在 ASCII 里，第一个值 72 对应大写字母 H。这样一个个对下去，就能解码整个文件。

动手：同一串数字，三种看法

存储器里永远只有左边那种 0 和 1；"文件格式"告诉程序该怎么读它们

第 1 节

WAV 文件：元数据和文件头

来看一个复杂一点的例子：WAVE 文件，也叫 WAV，它存储音频。要正确读取数据，我们需要先知道一些信息，比如码率，以及是单声道还是立体声。关于数据的数据，叫元数据（metadata）。这些元数据存在文件的最前面、在所有实际数据之前，这部分叫文件头（header）。

这是一个 WAV 文件开头 44 个字节的样子。有些部分总是一样的，比如拼出 W-A-V-E 的那一段；另一些部分是数字，会随文件里装的数据而变化。音频数据紧跟在元数据后面，存成一长串数字。这些数值代表每秒捕获很多次的声音振幅。如果想了解声音的基础知识，可以看我们物理速成课里讲声音的那一集。

举个例子，来看我说"hello!"的波形。现在我们捕获到了一些声音，放大其中一小段。数字麦克风，比如你电脑或手机里的那种，每秒对声压采样几千次，每个采样都可以表示成一个数字。数字越大，声压越高，这叫振幅。WAVE 文件里存的正是这些数字！每一秒的音频都有几千个振幅！播放这个文件时，音频程序需要驱动计算机的扬声器，让它发出原来的波形。"Hello!"

第 2 节

BMP：一个个像素

现在你开始熟悉文件格式了，我们来谈谈位图（bitmap），也就是 BMP，它存储图片。在计算机上，图片由很多叫像素（pixel）的小方块组成。每个像素是三种颜色的组合：红、绿、蓝。它们叫加色三原色，混合在一起，可以在电子屏幕上创造出任何其他颜色。

和 WAV 文件一样，BMP 也以元数据开头，包括图片宽度、图片高度和颜色深度这些关键值。比如，假设元数据说这张图宽 4 像素、高 4 像素，颜色深度 24 位——红 8 位、绿 8 位、蓝 8 位。提醒一下，8 位就是 1 个字节，一个字节能存的最小数是 0，最大是 255。

动手：一个字节一个字节地读出图片

读完以后可以点格子换颜色，右边的字节会跟着变。第一行的四个颜色来自课程，其余像素按第 21 集给出的条件反推（连续 7 个黄色等）

来看第一个像素的颜色：红是 255，绿是 255，蓝也是 255，也就是红、绿、蓝都是全强度，它们在显示器上混合成白色。所以第一个像素是白的！下一个像素的红绿蓝值——也就是 RGB 值——是 255, 255, 0，是黄色！再下一个的 RGB 值是 0, 0, 0，所有颜色都是零强度，也就是黑色。再下一个是黄色。因为元数据说这是一张 4×4 的图片，我们知道已经到了第一行像素的末尾，所以要换到下一行。下一个 RGB 值是 255, 255, 0，又是黄色。好，把这张 4×4 图片的所有像素都读出来——当当！一个分辨率很低的吃豆人！

这显然只是一张小图的简单例子，但我们完全可以把这张图存成一个 BMP。我想再强调一次：不管是文本文件、WAV、BMP，还是我们没时间讨论的更花哨的格式，在底层它们都一样：存在存储设备上的、一长串二进制数字。文件格式是读懂其中数据的关键。

文件扩展名不是格式本身 把 photo.bmp 改名成 photo.txt，里面的字节一个都没变，只是你的电脑会拿错误的格式去读它。程序真正判断格式，常常是看文件开头那几个固定的字节，比如 WAV 开头总是 "RIFF"，BMP 开头总是 "BM"，PNG 开头是 0x89 "PNG"。
第 3 节

把很多文件放进存储器：目录文件

现在你对文件更了解了，我们接着讲计算机怎么存放它们。虽然底层的存储介质可能是一条磁带、一个磁鼓、一张磁盘或者集成电路……软硬件的抽象让我们可以把存储器想成一长排存放数值的小桶。

早期，计算机一次只做一项计算，比如计算炮兵射程表，整个存储器就像一个大文件：数据从存储器的开头开始，随着输出的产生按顺序往后填，直到填满存储容量。然而，随着计算能力和存储容量的提升，同时存放不止一个文件变得可能，也变得有用。最简单的办法是把文件首尾相接地存放。这样可以……但计算机怎么知道每个文件从哪里开始、到哪里结束呢？存储设备没有"文件"的概念，它们只是存放大量位的机制。

所以，要让它行得通，我们需要一个特殊的文件，记录其他文件都在哪里。它有很多名字，一个比较通用的说法是目录文件（Directory File）。它通常就放在存储器的最前面，这样我们总知道去哪里找它——位置 0！

目录文件里有存储器中所有其他文件的名字。在我们的例子里，每个文件都有一个名字，后面跟一个点，再以所谓的文件扩展名结尾，比如"BMP"或"WAV"，它们进一步帮助程序识别文件类型。目录文件还存着这些文件的元数据，比如创建时间、最后修改时间、所有者是谁，以及能不能读、能不能写，或者两者都行。但最重要的是，目录文件记录着每个文件从存储器的哪里开始、有多长。

如果要添加文件、删除文件、更改文件名之类的，就必须更新目录文件里的信息。这就像书的目录：如果你把某一章改短了，或者挪到了别的地方，就得更新目录，不然页码就对不上了！目录文件以及对它的维护，是一个非常基础的文件系统的例子——文件系统是操作系统中负责管理和追踪存储文件的那部分。这个例子叫平面文件系统（Flat File System），因为所有文件都存在同一个层级上。它是平的！

第 4 节

块、碎片和碎片整理

当然，把文件首尾相接地挤在一起有点问题：比如我们想给"todo.txt"加点数据，就没有空间了，除非覆盖掉"carrie.bmp"的一部分。所以现代文件系统做两件事。

第一，它们把文件存在块（block）里。这会给改动留出一点额外空间，叫空闲空间（slack space）；也意味着所有文件数据都对齐到同一个大小，管理起来更简单。在这种方案里，目录文件需要记录每个文件存在哪个块里。

第二，文件系统允许把文件拆成几段，存在很多个块里。假设我们打开"todo.txt"，又加了几项，文件变得太大，一个块装不下了。我们不想覆盖相邻的块，于是文件系统分配一个没用的块来容纳多出来的数据。在这种文件系统方案里，目录文件要为每个文件存的不只是一个块，而是一个块列表。这样，文件就可以有各种大小，只要分配和释放块，就能轻松变大变小。如果你看过讲操作系统的那一集，这应该听起来很像虚拟内存。概念上确实非常相似！

动手：一个小文件系统

推荐顺序：加几项 → 删除 carrie.bmp → 再加几项（看碎片）→ 碎片整理 → 新建文件夹 → 移动文件。块的编号和课程画面不完全一样，过程相同

现在假设我们想删除"carrie.bmp"，只要把它的记录从目录文件里删掉就行了。这让一个块变成了空闲的。注意，我们并没有真的擦除存储器里这个文件的数据，只是删掉了它的记录。那个块迟早会被新数据覆盖，但在那之前，数据就一直待在那里。这就是计算机取证团队能从电脑里"恢复"数据的一种方式，哪怕人们以为它已经删掉了。狡猾！

好，假设我们往待办清单里加了更多项，文件系统又给这个文件分配了一个块，这次回收了从 carrie.bmp 释放出来的那个块。现在"todo.txt"存在 3 个块里，彼此隔开，而且顺序也乱了。文件像这样在存储器里被拆散，叫碎片化（fragmentation），它是文件被创建、删除、修改的必然副产品。对很多存储技术来说，这是坏消息：如果在磁带上，把 todo.txt 读进内存，需要先找到第一块，再快进到后面那块，再倒带回中间那块——来回折腾！在真实的文件系统里，大文件可能存在几百个块里，你可不想等五分钟才打开一个文件。

答案是碎片整理（defragmentation）！这听起来像一堆术语，但过程其实很简单，而且曾经看它运行非常有意思！计算机把数据来回复制，让每个文件的块在存储器里挨在一起、顺序正确。整理之后，我们可以一次快速地读出 todo 文件，它现在位于连续的几个块里。

第 5 节

分层文件系统

到目前为止，我们只讲了平面文件系统，所有文件都存在一个目录里。当计算机只有一点点存储空间、你可能只有十几个文件时，这还行得通。但就像上一集讲的，存储容量爆炸式增长，计算机上的文件数量也是。很快，把所有文件都放在同一层就变得不切实际了。

就像现实世界里的文件一样，把相关的文件放进文件夹会很方便，然后还可以把相关的文件夹放进文件夹，以此类推。这就是分层文件系统（Hierarchical File System），你的电脑用的就是它。实现方式有很多种，我们沿用前面的例子来说明主要思路。

最大的变化是，目录文件不仅要能指向文件，还要能指向其他目录。为了区分哪个是文件、哪个是目录，需要一些额外的元数据。最上面的这个目录文件叫根目录（Root Directory），所有其他文件和文件夹都沿着不同的文件路径位于它下面。可以看到，我们的根目录文件里有 3 个文件和 2 个子目录：music 和 photos。如果想看 music 目录里存了什么，就得去那个块，读那里的目录文件，它的格式和根目录一样。里面有好多好歌！

除了能建立无限深度的层级，这种方法还让我们能轻松地移动文件。如果想把"theme.wav"从根目录移到 music 目录，不需要重新排列任何数据块，只要修改两个目录文件：从一个里删掉一条记录，在另一个里加上一条。重要的是，theme.wav 文件还待在原来的块里。（上面的模拟器里试过了吗？）

以上就是文件系统关键原理的快速概览。它们提供了又一种往上提升一层抽象的方式：文件系统让我们不必面对存在磁带、旋转磁盘之类东西上的原始位，而是把数据想成整齐有序、方便访问的文件。我们甚至开始讲用户——而不是程序员——操作数据，比如打开文件、整理文件，这预示了接下来几集的方向。下周见！

在你的电脑上 你在终端里看到的 /Users/你的名字/Desktop/a.txt 就是一条从根目录 / 一层层往下的路径。mv 一个大文件到同一块硬盘的另一个文件夹几乎是瞬间完成的，就是因为它只改了目录记录；而复制到 U 盘要慢得多，因为那才是真的在搬数据。固态硬盘读取不同位置一样快，所以现在基本不需要手动做碎片整理了。
第 6 节

本集小结

概念要点
文件格式约定数据怎么排、怎么读；底层都是一长串二进制
TXT每个数按 ASCII 对应一个字符（72 → H）
WAV44 字节文件头（元数据：声道、采样率……）+ 一长串振幅
BMP元数据（宽、高、颜色深度）+ 每个像素 RGB 三个字节
目录文件放在位置 0，记录每个文件的名字、元数据、起始位置和长度
块文件按块存放、可跨多个块；目录记录块列表；删除只删记录
碎片 / 整理增删改让文件的块散开、乱序；整理把它们排回连续、有序
分层文件系统目录也能指向目录；根目录；移动文件只改两个目录文件
一句话 文件格式让一串数字有了意义；文件系统用一个"目录文件"记录每个文件在哪些块里，让我们把一排存储桶看成一个个有名字、能放进文件夹的文件——又一层抽象。

合上页面，试着回答

1. 什么是元数据？WAV 文件为什么需要文件头？
关于数据的数据。不知道采样率、单声道还是立体声、每个采样几位，后面那串数字就没法正确播放。这些信息放在文件最前面，叫文件头。
2. 24 位颜色深度的 BMP，一个像素占几个字节？255, 255, 0 是什么颜色？
3 个字节：红、绿、蓝各 1 个字节（0~255）。255, 255, 0 是全强度的红加全强度的绿，没有蓝——黄色。
3. 为什么"删除"的文件有时能被恢复？
删除只是把文件的记录从目录文件里去掉，块被标成空闲，里面的数据并没有被擦除，直到某天被新数据覆盖。在那之前，取证工具可以把它读回来。
4. 在分层文件系统里，把文件从一个文件夹移到另一个，数据块要动吗？
不用。只要在原文件夹的目录文件里删掉这条记录、在目标文件夹的目录文件里加上，文件的数据还在原来的块里。
