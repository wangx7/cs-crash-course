第 0 节

软件工程是什么

这个系列里我们讲了很多排序，给一串数字排序的代码往往只有十来行，一个程序员很容易写出来。而且它短到不需要任何专门的工具——用记事本就能写。真的！

但排序算法本身不是一个程序，它很可能只是一个大得多的程序里的一小部分。比如，微软 Office 大约有 4000 万行代码。4000 万！任何一个人都不可能把它全部弄懂、写出来！为了构建这样的大型程序，程序员会使用一整套工具和做法，合起来形成了软件工程（Software Engineering）这门学科。这个词由工程师玛格丽特·汉密尔顿（Margaret Hamilton）创造，她帮助 NASA 在阿波罗登月任务中避免了一些严重问题。她曾这样解释：

"这有点像根管治疗：你一直拖到最后，可其实有些事你本可以提前做。就像预防性的医疗保健，只不过这是预防性的软件。"—— 玛格丽特·汉密尔顿
第 1 节

面向对象：把函数打包成层级

第 12 集提过，把大程序拆成小函数，可以让很多人同时工作。他们不用操心整个项目，只需要关心自己正在写的那个函数。所以如果你的任务是写一个排序算法，你只需要确保它排得正确、排得高效。

然而，光把代码打包成函数还不够。微软 Office 里大概有几十万个函数，虽然比 4000 万行代码好对付，但对一个人或一个团队来说，要管的"东西"还是太多了。解决办法是把函数打包成层级，把相关的代码放在一起，组成对象（object）。

比如，汽车的软件里可能有好几个和定速巡航有关的函数：设定速度、把速度往上或往下微调、彻底关掉定速巡航。因为它们都相关，我们可以把它们包装成一个统一的"定速巡航对象"。但我们不必止步于此：定速巡航只是引擎软件的一部分，可能还有控制火花塞点火、燃油泵和散热器的几组函数。所以我们可以创建一个"父"对象——引擎对象，包含所有这些"子"对象。除了子对象，引擎本身也可能有它自己的函数，比如启动和关闭引擎；也会有它自己的变量，比如汽车已经行驶了多少英里。总的来说，对象可以包含其他对象、函数和变量。当然，引擎也只是"汽车对象"的一部分，还有变速箱、车轮、车门、车窗等等。

作为程序员，如果我想设定定速巡航，就沿着对象层级往下走，从最外层的对象一路走到嵌套得越来越深的对象，最后找到想调用的函数："汽车，然后引擎，然后定速巡航，然后把巡航速度设为 55"。编程语言里常常用类似下面这样的写法。

把功能单元打包进嵌套对象的这种思想，叫面向对象编程（Object Oriented Programming）。这和我们整个系列一直在做的事非常相似：把底层细节封装进更高层的组件里，隐藏复杂性。以前我们把晶体管电路打包成更高层的逻辑门，现在我们对软件做同样的事。又一次，这是往上提升一层抽象的方式！

把一个大程序——比如汽车软件——拆成功能单元，非常适合团队合作。一个团队可能负责定速巡航系统，团队里的一个程序员负责其中几个函数。这和建造摩天大楼这种巨大的实体建筑很像：有电工布电线，管道工装水管，焊工焊接，油漆工刷漆，还有成百上千的人在楼体上忙来忙去。他们发挥各自的技能，同时在不同的部分工作，直到有一天，整栋楼都能用了！

第 2 节

API 与 public / private

回到定速巡航的例子：它的代码需要用到引擎软件其他部分的函数，才能让车保持恒定的速度。那部分代码不归定速巡航团队负责，是另一个团队的代码。因为不是自己写的，定速巡航团队需要好的文档，说明那些代码里每个函数是做什么的，还需要一个定义清楚的应用程序编程接口（Application Programming Interface），简称 API。你可以把 API 看作合作的程序员们在代码各个部分之间打交道的方式。

比如，在 IgnitionControl（点火控制）对象里，可能有设置发动机转速的函数、检查火花塞电压的函数，以及点燃单个火花塞的函数。能设置发动机转速非常有用，定速巡航团队会需要调用这个函数。但他们对点火系统的工作原理了解不多，让他们去调用点燃单个火花塞的函数可不是好主意，引擎可能会爆炸！也许吧。

API 让合适的人访问合适的函数和数据。面向对象的编程语言通过让你指定函数是 public（公开）还是 private（私有）来做到这一点。如果一个函数被标为 private，就意味着只有这个对象内部的函数才能调用它。所以在这个例子里，只有 IgnitionControl 内部的其他函数，比如 setRPM，才能点燃火花塞。另一方面，因为 setRPM 函数被标为 public，其他对象——比如定速巡航——就可以调用它。

这种隐藏复杂性、并有选择地公开的能力，是面向对象编程的精髓。它是构建大型复杂程序的一种强大而流行的方法。你电脑上几乎所有的软件、游戏机上运行的几乎所有游戏，都是用面向对象的编程语言写的，比如 C++、C# 或 Objective-C。你可能听说过的其他流行的"OO"语言还有 Python 和 Java。

前端里的 API 你写的 Vue 组件也是这个思路：props 和 emit 的事件是对外公开的接口，组件内部的状态和方法别人碰不到。后端提供的"接口文档"，就是前后端两个团队之间的 API。
第 3 节

集成开发环境与调试

有一点很重要：代码在编译之前，只是一堆文字而已。前面说过，你可以用记事本或者随便哪个文字处理软件写代码，确实有人这么做。但一般来说，今天的软件开发者用的是专门写程序的应用，里面集成了很多编写、整理、编译和测试代码的有用工具。因为它把你需要的一切都放在一个地方，所以叫集成开发环境（Integrated Development Environment），简称 IDE。

所有 IDE 都提供写代码用的文本编辑器，通常带有一些有用的功能，比如自动给代码上色，提高可读性。很多 IDE 甚至会在你打字时检查语法错误，就像代码的拼写检查。大型程序包含大量单独的源文件，所以 IDE 让程序员可以整理、高效地浏览所有文件。IDE 里还直接集成了编译和运行代码的功能。如果你的程序崩溃了——因为它还没写完嘛——IDE 能带你回到出事的那一行代码，并且往往会提供额外的信息，帮你追踪并修复这个 bug，这个过程叫调试（debugging）。

第 4 节

文档与注释

除了写代码和调试，程序员工作中另一个重要部分是给代码写文档。可以写在单独的文件里，通常叫 README，告诉其他程序员在深入代码之前先读这个帮助文件。也可以直接写在代码里，叫注释（comment）：注释是特别标记过的语句，程序在编译代码时会忽略它们，它们存在的唯一目的，就是帮助程序员弄清源代码里什么是什么。

好的文档不仅能帮程序员回头看自己很久没碰过的代码，对完全没接触过这些代码的程序员也至关重要。我想在这里花一秒钟再强调一下：最糟糕的就是有人把一堆没注释、没文档的代码丢到你手上，你只能一行一行地读，才能弄懂它在做什么。说真的，别做那种人。

文档还能促进代码复用。程序员不必一遍遍地重复写同样的东西，可以找到别人写好的、正好满足需要的代码。然后多亏了文档，他们可以直接把它用进自己的程序，根本不用读那些代码。正如大家常说的："去读文档！"（Read the docs）

第 5 节

版本控制

除了 IDE，另一种帮助大团队协作开发大型项目的重要软件叫源代码管理（Source Control），也叫版本控制（version control）或修订控制。在苹果或微软这样的大型软件公司，项目代码通常存在中心服务器上，叫代码仓库（code repository）。当程序员想修改一段代码时，可以把它借出（check out），有点像从图书馆借书，这通常可以直接在 IDE 里完成。然后他们可以在自己的电脑上随意编辑这段代码，加新功能、测试它们能不能用。当程序员确信改动没问题、没有遗漏时，就可以把代码交回代码仓库，这叫提交（commit），供其他所有人使用。

当一段代码被借出、大概正在被更新或修改时，其他程序员就不去碰它。这能防止奇怪的冲突和重复劳动。这样，成百上千的程序员可以同时借出和提交一段段代码，一点点迭代出庞大的系统。

动手：提交、发现 bug、回滚

关键在于，你不希望有人提交有 bug 的代码，因为其他人、其他团队可能依赖它，他们的代码可能会崩溃，造成混乱、浪费时间。存在服务器上的代码主版本（master），应该始终能无错误地编译，并且运行时 bug 尽可能少。但有时 bug 还是会混进来。幸运的是，源代码管理软件会记录所有的改动，如果发现了 bug，整个代码或者其中一部分可以回滚（roll back）到之前某个稳定的版本。它还会记录每处改动是谁做的，这样同事们就可以给惹祸的人发去讨厌的——我是说，有帮助的、鼓励性的——邮件。

今天的版本控制 课程讲的"借出期间别人不能动"是早期集中式工具的做法。今天最常用的是 Git：每个人都有完整的仓库副本，大家可以同时改同一个文件，提交时再合并（merge），改到同一行才需要手动解决冲突。你的这个学习仓库、以及本图文版最后放到 GitHub 上，用的就是 Git。
第 6 节

质量保证：alpha 和 beta

调试和写代码密不可分，通常由个人或小团队完成。放眼全局的调试叫质量保证测试（Quality Assurance testing），简称 QA：由一个团队严格地测试一款软件，试图制造各种意想不到的情况把它绊倒。基本上，就是把 bug 引出来。把所有毛病都抚平需要巨大的努力，但这对确保软件在发布前、在尽可能多的情况下、为尽可能多的用户按预期工作至关重要。

你可能听说过 beta 版软件。这是基本完成、但没有百分之百完全测试过的版本。公司有时会向公众发布 beta 版来帮助发现问题，这基本上相当于得到了一支免费的 QA 团队。你不太常听说的，是 beta 之前的那个版本：alpha 版。它通常粗糙得很、bug 一大堆，只在公司内部测试。

以上只是软件工程师用来构建我们今天熟知和喜爱的大型软件——比如 YouTube、《侠盗猎车手 5》和 PowerPoint——的那些工具、技巧和技术的冰山一角。你可能想到了，这几百万行代码需要相当强大的处理能力才能以有用的速度运行，所以下一集我们来讲计算机是怎样变得如此之快的。到时见！

第 7 节

本集小结

问题软件工程的办法
代码太多，一个人管不过来拆成函数，再按层级打包成对象（面向对象编程）
要用别的团队的代码文档 + 定义清楚的 API；public 公开、private 只给内部用
写代码、找 bug 效率低IDE：上色、语法检查、整理文件、编译运行、调试定位
代码过一阵就看不懂、别人也看不懂README、注释；"去读文档"促进复用
很多人同时改代码版本控制：仓库、借出、提交、记录作者、出错回滚
上线前尽量没 bugQA 测试；alpha 内部测，beta 请公众帮忙测
一句话 软件工程是让很多人一起造出大软件的那套工具和做法：用对象和 API 隐藏复杂性、有选择地公开功能，用 IDE、文档、版本控制和 QA 防患于未然——正如汉密尔顿说的，"预防性的软件"。

合上页面，试着回答

1. 为什么光把代码拆成函数还不够？对象解决了什么？
大软件会有几十万个函数，还是太多。对象把相关的函数和变量打包在一起，并且可以层层嵌套（汽车 → 引擎 → 定速巡航），每个团队只需关心自己那一块。
2. setRPM 是 public、fireSparkplug 是 private，这样设计有什么好处？
别的团队（定速巡航）只需要、也只能调用 setRPM 这种安全的高层功能；直接点火花塞这种危险的底层操作只能由点火控制对象内部调用。API 让合适的人访问合适的函数，隐藏复杂性，也防止误用。
3. 为什么说调试工具很重要？
大多数程序员 70%~80% 的时间花在测试和调试上，而不是写新代码。IDE 能在出错时直接定位到那一行并给出信息，大大节省时间。
4. 版本控制除了让很多人同时工作，还有什么用？
它记录了所有改动和改动者。有人提交了有 bug 的代码时，可以把整个或部分代码回滚到之前的稳定版本，并且知道是谁改的。
